## 4. Entity codebook

Target Entity           : E_target(q)     = 0.55 + 0.40q    → 8bit 140-242

**このcodebookは変更しない。** 帯の使い方はarmごとに異なる（§13参照）。

### 予約帯

```
124 - 131 は最終テンソルに存在してはならない

### Renderer / Style split

**R = Renderer、S = Style。** カメラ運動 / 被写体運動ではない。

RendererとStyleを**別変数**として扱う。交絡させない。

| split | Renderer | Material / Lighting | 今月 |
|---|---|---|---|
| **R0S0** | **EEVEE** | set A | Train / IID |
| **R1S0** | **Cycles** | set A | 生成のみ（評価は9月） |
| **R0S1** | **EEVEE** | set B | 生成のみ（評価は9月） |
| R1S1 | Cycles | set B | やらない |

**R0 = EEVEE、R1 = Cycles（2026-08-04 確定）。** rev.3 の向き（R0 = Cycles）から反転した。

学習に使う側（R0）を EEVEE にする理由。

| # | 理由 |
|---|---|
| 1 | **フリッカーがゼロ。** Cycles はサンプル不足でフレーム間ノイズが乗り、デノイザは時間的に不安定 |
| 2 | **§12 の State coherence が測れる。** 学習ターゲット自体が揺れていると「フリッカー」を生成側の破綻として測る設計が自己矛盾になる |
| 3 | 決定性が上がり §15 Determinism floor に有利 |

Cycles を「ベースモデルの分布に近い」ため R0 にする案もあるが、
それは全 arm 共通で床が上がるだけで B vs C の比較には効かない。1と2を優先する。

**R1（Cycles）側の必須設定。** 学習には使わないが**評価の参照動画（GT）として
使う**ため、フリッカー源を全部切る。参照側が揺れていると §12 の State coherence が
測れない。

| 設定 | 値 | 理由 |
|---|---|---|
| サンプル数 | 高め（要試写。暫定512） | 少ないとフレーム間ノイズ |
| デノイズ | **無効** | フレーム独立に効くので時間的な揺れを作る |
| Adaptive Sampling | **無効** | フレームごとにサンプル数が変わると揺れの量も変わる |
| **Noise Seed（Animate Seed）** | **固定** | 既定でフレームごとに変わる。固定するとノイズが静止する |

**材質は Principled BSDF のみで組む。** EEVEE 専用 / Cycles 専用ノードを使うと
意図しない差が混ざり、Renderer shift の解釈ができなくなる。
Color Management も両者で同一に固定する（§22.3）。

全split共通で固定：`Geometry / Animation / Camera trajectory / Object identity / frame数 / 画角`

変えてよいのは Renderer または Style のどちらか一方だけ。

### split の適用範囲（2026-08-04 確定）

§22 の「幾何パスは EEVEE」と Renderer 軸の両立は、次の切り分けで解消する。

| 対象 | split の影響 | レンダラ |
|---|---|---|
| **Target video**（モデルが生成する側の正解映像） | **受ける** | split に従う（**R0=EEVEE / R1=Cycles**） |
| **Control Video（Arm A / B / C）** | **受けない。全splitで同一** | **EEVEE 固定** |
| **評価GT パス**（Position / Depth / Object ID / Visibility / Mask） | **受けない。全splitで同一** | **EEVEE 固定** |

**理由。** Control 側にも split を効かせると、Arm A（クレイ＝レンダー）だけ
Control に domain shift が乗り、Arm B / C には乗らない。
Renderer shift 評価が arm 間で非対称になり、§2 の
「異なるのはControl Videoのみ」という前提が崩れる。

サンプル平均の弊害（輪郭に実在しない中間座標が出る）は幾何パスに固有の問題であり、
Target video の RGB では AA として望ましい。
よって Target video に Cycles を使うことは §22 と矛盾しない。

**R1S0 の出力構成。** 1つの `.blend` からレンダラを切り替えて2回焼く。

```

## 11. M_invariant（空間的不変領域）

物体編集時、以下すべてを満たす画素だけを不変領域とする。

```
M_invariant =
      Non-target または Background            ← id パスで決まる
  AND Original と Edited の両方で可視           ← id パスで決まる
  AND 深度順序が同一                           ← depth パスで決まる
  AND 同じ表面を観測している                    ← id + depth で決まる
  AND Target シルエットから 2px より外          ← id パスの膨張で決まる（rev.7 追加）
  AND GT-original と GT-edited の差が許容値以下  ← §18-7
```

**除外**：新規遮蔽領域 / 新規出現領域（disocclusion）/ 異なる表面が見える領域 /
正当に影・反射が変化した領域 / 深度順序が変化した領域 /
**Target シルエット近傍 2px（AA フリンジ）**

### 実装（Scene C での畳み込み）

Target 以外は全部静止・カメラ固定なので、前4条件は id と depth だけで決まる。

| 条件 | 実装 |
|---|---|
| Non-target / Background | `id_orig != 3` かつ `id_edit != 3` |
| 両変種で可視・同一表面・深度順序同一 | `id_orig == id_edit` かつ `|depth_orig − depth_edit| < 1e-4` |
| Target 近傍の除外 | `(id_orig == 3) or (id_edit == 3)` を city-block 2px 膨張した領域を除く |

depth の許容値 `1e-4` は float32 前提（作法 #21）。`id` が一致すれば depth も一致する
はずなので、**ここで落ちる画素があったら幾何パスの異常**として扱う（W3 実測では 0 件）。

### 許容値：**2**（8bit、RGB チャンネルの max）

**決め方は「谷」ではなく「不感」。** W3 実測（§32.1）で、許容値を 0 から 32 まで
動かしても M_invariant 面積は画面の 0.089% しか変わらない。半影は連続量なので
ヒストグラムに谷が出ず、閾値では決められない。下端に置いて残りを幾何条件に任せる。

論文には感度表（§32.1）を載せ、**結論が許容値に依存しないこと**を示す。

**許容値 0（bit 完全一致）は採らない。** R1（Cycles / 512 sample / denoise 無効）では
サンプルノイズで何も bit 一致せず、split をまたいだ時に mask が崩壊する。

### mask は R0S0 で確定し、全 split で同一の画素集合を使う

M_invariant は**編集の性質**であってレンダラの性質ではない。split ごとに作り直すと
測定領域が変わり R0/R1/S1 を横比較できなくなる。R1 の Cycles ノイズは mask を削る
のではなく、**spillover の noise floor として別に測って報告する**（§29）。

### §18-7 で使う指標と §16.8 で使う指標は違う

| 用途 | チャンネルの畳み込み | 理由 |
|---|---|---|
| M_invariant の除外判定（§11） | **max** | 1チャンネルでも動いたら不変ではない |
| Arm C の色誤差（§16.8） | **mean** | 「色がどれだけ化けたか」の量。過去の 11.30 / 2.29 と接続するため |

**混ぜてはいけない。**

## 12. 評価指標

> **注意。** ここは**生成映像**の評価指標。
> **Control表現がVAEを生き延びるか**の指標（色誤差 / identity）は §13・§16 側。
> 2つを混同しない。

### Control fidelity（物体制御）

Target center trajectory error / 最終位置誤差 / 移動方向 / 速度 /
Target Mask IoU / 遮蔽後の再出現位置 / 軌跡連続性

### State coherence

対象数 / 複製 / 消失 / フリッカー / 形状崩壊 / Track切断 / テレポート /
ID switch / Target-Non-target identity混同 / 遮蔽後の再取得 /
判定不能 / Tracker failure

**自動検出器の失敗と、生成映像そのものの破綻を分離して記録する。**

### Spatial spillover（M_invariant内で測定）

LPIPS / PSNR / SSIM / DINO feature drift / 非対象物体の位置変化

### Absolute usability threshold

**Control fidelity は 7 指標、State coherence は 12 項目であり、いずれもスカラーでは
ない。** rev.9 までの `≥ T_control` という書き方は型として成立しておらず、不等号の
向きも誤っていた（軌道誤差は小さいほど良い）。**代表 1 指標をゲートにし、残りは報告
のみとする**（案 6-C。2026-08-09 確定。§37）。

| | 式 | 面 |
|---|---|---|
| **T_control** | **median Target center trajectory error ≤ 47 px** | Scene C′、GT で Target 可視な 44 フレーム（0–35 / 41–48） |
| **T_coherence** | **Target 検出個数 ≠ 1 のフレーム率 ≤ 2 / 44** | 同上。Tracker failure は分母から除外し別カウント |

| 項目 | 値 | 根拠 |
|---|---|---|
| 47 px の由来 | Target の等価円半径 94.5 px の **50%**（面積 28,029 px。§33.4） | d/r = 0.5 で IoU 0.52。「半分以上重なっている」が下限 |
| 2 / 44 の由来 | **幾何的に判定困難なフレーム数と同数**（frame 35 / 41。§26） | 個数を外すのが表現の問題でなく遮蔽の問題である本数のみを予算とする |
| 統計量 | **median を主、p95 を副** | 検出器の失敗フレームが max を支配するため mean も max も使えない |
| 完全遮蔽 36–40 | **別枠。誤差ではなく「消えているべき」の有無を検査** | 中心誤差が定義できない |

**保険条項。** Evaluator floor（§15 / §18-9）は未測定である。
**検出器自体の中心誤差 p95 が 47 px 以上なら、この関門を撤回し floor をそのまま
報告する。閾値を測定後に緩めることは事後合わせであり禁止する。**（§37.8）

**帯反転・予約帯画素の扱いは §13・§16 側の別指標であり、ここには混ぜない**
（§37.9。案 27-B）。

### 13.4 順投影と遮蔽判定（2026-08-04 確定）

**Arm C は「6px固定のスクリーン空間円」を描くため、3D→screen の順投影が必要。**
§22 が「Arm B / C から fov 経路が消えた」と書いているのは **Arm B のみ正しい。**
Arm C は投影を通るので、既知バグ #1（matrix_world のScale焼き込み）と
#2（fov誤記録）の経路が生きている。

#### 順投影：`world_to_camera_view` を使う。手書きの intrinsics を組まない

```python
from bpy_extras.object_utils import world_to_camera_view
ndc = world_to_camera_view(scene, camera, world_coord)
u = ndc.x * W
v = (1.0 - ndc.y) * H        # 戻り値は左下原点。画像の行は上から
```

**`(1 - ndc.y)` を忘れるのが上下反転バグの唯一の発生点。**
`world_to_camera_view` は内部で `matrix_world.normalized()` を使うため、
Scale が焼き込まれていても正規化される。fov も Blender 自身が計算する。
これで既知バグ #1・#2 の経路が Arm C からも消える。

**実測（W2a-3a）。** 素の式との比較 882 組（18点 × 49フレーム）。

| 項目 | 実測 |
|---|---|
| max err u | **0.000029 px** |
| max err v | **0.000021 px** |
| 許容 0.01 px 超え | **0** |

#### 遮蔽判定：`scene.ray_cast` を使う。Depth パス比較は採用しない

```python
vec = world_pt - camera_world_location
hit = scene.ray_cast(depsgraph, camera_world_location,
                     vec.normalized(), distance=vec.length - 1e-3)[0]
visible = (not hit) and 点が画面内
```

自己ヒット回避の `1e-3` 以外にパラメータを持たない。

**Depth パス比較を採用しない理由（W2a-3a 実測）。**

斜めに見える面では、1画素の中で深度が大きく変化する。

| 条件 | 面の画面幅 | 1画素あたりの深度勾配 |
|---|---|---|
| 立方体の +X 側面（index 0） | 15.06 px | **0.066 / px** |
| 同（index 3） | 12.46 px | **0.080 / px** |

点が画素中心から 0.28 px ずれているだけで、画素中心の深度は
`10 − 0.28 × 0.0664 = 9.981`（実測 9.982）となり、点の深度 10.000 より小さくなる。
結果として「点が奥にある＝遮蔽」と誤判定する。

| 方式 | 幾何期待値との誤り（294判定中） |
|---|---|
| Depth パス比較 | **8** |
| **`ray_cast`** | **0** |

許容値を 0.05 に上げればこのシーンでは通るが、薄い物体や接触面があるシーンでは
破綻する。**必要な許容値がシーンの幾何に依存する時点で固定値にできない。**

#### 描画順：深度の遠い順に描く

近い点が遠い点を上書きする。同一画素に複数の点が落ちた場合、近い点の色が残る。
上書きされた点は §16.7 の採点母数から除外する。

**実シーンでは発動しない場合がある。** 極小シーンでは遮蔽板の点と Target の点が
画面上で重なるフレームが存在しない（遮蔽板がある場所では背後の Target が隠れるため）。
発動しないコードパスを検証済みとしないため、合成データで単体テストする（§25）。

#### 出力：PNG を自前実装で書く

Blender の画像保存はカラーマネジメントを通るため、8bit 値がそのまま出る保証がない。
さらに **Blender で書いて Blender で読むと同じ変換が往復で打ち消され、
誤っていても検出できない。** §17 バグ#4（mp4 経由で画素値が変わる）と同型。

```
zlib / 8bit RGB / filter type 0（None）/ 非インターレース
書き込みと読み戻しの両方を自前実装し、byte 一致を assert する
```

外部ツール互換も確認済み（OpenCV で読んで値が一致）。

#### 正面性フィルタは採用しない（2026-08-04 確定。§18-19）

**面が真横に近い点も `ray_cast` の判定どおり可視として扱う。** `n·v > 閾値` による除外は入れない。

| # | 理由 |
|---|---|
| 1 | **ちらつきは構造的に起きない。** W2b の制約で `rotation = 0` 固定のため、n·v が変化する原因は遠近による視線方向の変化だけ。極小シーンの +X 側面では index 0 で +0.13、index 約17 で 0、index 48 で −0.22 と**単調に1回ゼロを跨ぐ**のみ。往復しない。再出現は §13 で「必須」と規定した設計仕様であり、1回の消失は異常ではない |
| 2 | **実害は角度ではなく距離。** ゼロ交差付近で面のスクリーン幅は 15 px → 0 px に潰れ、その面の点が数画素に集まる。結果は (a) 深度ソートによる上書きで §16.7 の採点母数から脱落、(b) 局所占有率が §13.4 の警戒線 30% を超える、(c) 24px 以内の隣接点数の急増による衝突グラフの密化。いずれもスクリーン距離で直接制御できる |
| 3 | **輪郭の非対称性。** n·v が小さい領域＝シルエット近傍。輪郭は §22.3 で本研究最重要領域と規定している。Arm B は Position パスで輪郭を全画素保持するため、Arm C だけ輪郭の点が系統的に消えると Primary comparison（B vs C）が非対称になる |
| 4 | **共有頂点では n·v が定義できない。** Arm C の点は `bpy` の頂点座標。立方体の角頂点は3面を共有し平均法線が斜めになるため、側面が真横でもフィルタを通過する。n·v を使うには「点を面内サンプルにする」という上流の決定が別途必要になる |
| 5 | **W2a の回帰基準値が無効化する。** 描画点数 14 / 8 / 10 と隠れ区間 [18, 30] は「幾何期待値と一致する」ことに価値がある。閾値を入れると幾何期待値そのものが閾値付きになり、検証性が落ちる |

**却下した論拠の残り。** 82.6° での `ray_cast` の数値安定性は極小シーン1件（294判定中誤り0）しか根拠がない。
密なメッシュでレイが隣接面をかすめる状況では変わる可能性がある。
**対応：先回りして点を削らず、n·v を記録して事後に分布を見る。**

```
n·v は各点 × 各フレームで JSON に記録する。可視判定・描画には一切使わない。
実シーンで可視判定が幾何期待値と食い違った点が出た場合、その n·v 分布を見る。
```

#### 点の選定：全フレーム和での最小スクリーン間隔 d（2026-08-04 新設）

```
候補点を貪欲に選ぶ。既に採用済みの点との間で、
どこか1フレームでも「両方可視かつ画面上 d px 未満」になるなら棄却する。
```

| 性質 | 内容 |
|---|---|
| パラメータ | スクリーン距離 d のみ（px）。無次元角度より単位が素直 |
| 計算 | 全フレームの和で1回。§13.4 の彩色（衝突グラフ）と同じ構造・同じループを流用する |
| 副作用 | 幅0に潰れる面の点は自動的にほぼ全部落ちる。角度を見ずに混雑だけが消える |
| 輪郭 | シルエット近傍の点は1個だけ残る。系統的には消えない |

### 13.6 色の付け方を「位置由来」から変更した理由

位置の符号化はArm Bの担当。よって色が位置を表す必要はない。

#### 16.10 劣化は位置ズレではなく色の希薄化である

復元フレーム t を正解フレーム t+δ で照合した。

|---:|---:|---:|---:|---:|---:|

| 10 | 17.3% | 17.2% | **59.4%** | 18.2% | 16.9% |
| 17 | 17.5% | 18.2% | **48.4%** | 17.6% | 17.7% |
| 34 | 17.9% | 17.9% | **52.0%** | 18.0% | 17.8% |

**点は正しい位置にあり、経路上に伸びた足跡も生じていない。**
失われているのは位置ではなく色である。

#### 16.12 identity は点密度に汚染される（主指標を変更した根拠）

半径3・1872点 と 半径3・480点 は**半径も速度も同一で、点数だけが違う。**

| V=17 | 1872点 | 480点 | 差 |
|---|---:|---:|---:|
| identity | 49.3% | 85.7% | **+36.4** |
| 色誤差 | 29.77 | 23.73 | −6.0 |

identity が36ポイント動くのは、近傍の紛らわしい相手が減ったためであり、
点の品質は変わっていない。一方、半径3・480点 と 半径6・480点 は
点数・近傍構造が同一で半径だけが違い、色誤差が半減する（23.73 → 11.30）。

```
identity = 点の品質 × 近傍の紛らわしさ   ← 混合物
色誤差   = 点の品質そのもの               ← 分離済み
```

Arm A / B / C は表現の密度が本質的に異なる。
**Arm間の横比較には色誤差を用いる。identity は使わない。**

identity を報告する場合は必ず次を添える。

- 点数と平均近傍数
- 同一条件の V=0 ベースライン（絶対値ではなく落差で読む）

#### 16.14 結論

1. Arm C の点表現は、VAE の時間方向4:1圧縮によって色が希薄化する。
   運動そのものは無害であり、劣化は圧縮に起因する。
2. 劣化は位置の誤りではなく色の希薄化であり、時間方向の補償では回復しない。
3. 点半径を 3px → 6px にすると、V=17 px/frame でも色誤差は判定基準の半分以下。
   **半径6を採用する。**
4. identity復元率は点密度に依存するため、Arm間比較の主指標に用いてはならない。
   **色誤差を用いる。**

#### 16.15 限界（論文の Limitations に書く）

1. **往復テストは代理指標である。** LoRA が消費するのは潜在であり、復元画素ではない。
   デコーダで復元できない情報が潜在にまったく無いとは限らない。保守的な設計指標として扱う。
2. **運動モデルは一様並進で、視差がない。** 実シーンではカメラ運動により手前と奥で
   速度が異なる。得られた V_max は楽観側の値である。
3. **V_max の上限は未測定。** 半径6で17を超える速度は試していない。「V_max ≥ 17」は下限の主張。
4. **半径9の標本が小さい。** 採点対象が毎フレーム73〜87点で、誤差は約±3.5ポイント。
5. **GPU間で約0.3ポイントの差が出る。** bf16 演算のハードウェア差。これ以下は有意でない。
6. **ズレ量は半径をまたいで比較できない。** 点が大きいほど同色画素が広範囲に存在するため、
   指標の床が半径とともに上がる。
7. **半径6での点数上限は未測定。** 全画面480点でのみ測定した。
8. **半径6と半径9を Scene C で比較していない。** §16.11 の半径比較は W1 の
   合成データ・全画面占有率 12.8% で行ったものである。半径6を維持する判断
   （§16.16）は Scene C での r9 実測ではなく、占有率という固定資源の配分の
   議論に基づく。

#### 16.16 半径9を採らなかった理由（§18-18 の決着。2026-08-06）

§16.11 の色誤差だけを見れば r9（V=17 で 5.66）は r6（11.30）より良い。
それでも r6 を採る。理由を明文化する。

**占有率は固定資源であり、半径はその配分を決める変数である。**
r9 は「1点あたりの色の頑健さ」を買い、その代金を「点数」で払う。
W3 の実測（§32）では**色誤差の余裕は 5.6 倍あり、点数は不足側だった。**
配分の向きが逆である。

##### 前提：同一占有率での点数換算

| 半径 | 円盤面積 | 面積比 | 同一占有率での点数 |
|---|---|---|---|
| **6** | **113 px** | **1.000** | **240（Target 72 / Non-target 168）** ← 実測 |
| 9 | 253 px | 2.2389 | **107（Target 32 / Non-target 75）** ← 換算 |

円盤面積は §28.3 の実測（半径3 → 29 / 半径6 → 113 / 半径9 → 253）。
点数は Scene C の実測値（§32.2）を面積比で割った換算値であり、実測ではない。

##### 理由1：色誤差の余裕は在庫過剰であり、r9 が買うものに需要がない

| 項目 | 値 | 出所 |
|---|---|---|
| 判定基準 | 24 | §16.8（最小色間距離 48.1 の半分） |
| r6 / Scene C の最悪（temporal / Target 帯） | **4.271** | §32.2 |
| 余裕 | **5.6 倍** | 同上 |
| 基準 24 に達する速度 | **V ≈ 38.9 px/frame** | §32.3 |
| §13 の設計速度上限 | 20 px/frame | §13 |

**設計上限の約 2 倍の速度まで基準に触れない。** r9 で色誤差をさらに半減させても、
使われない余裕が増えるだけである。

##### 理由2：不足しているのは点数のほうである

Scene C では Target が遮蔽される区間があり、可視 Target 点数はフレームによって
0 まで落ちる（§32.6）。**点数はすでに下限に張り付いている資源である。**

| index | 34 | 35–41 | 42 | 43 | 44 | 45 | 46 | 47 | 48 |
|---|---|---|---|---|---|---|---|---|---|
| **r6（実測）** | 6 | **0** | 2 | 2 | 7 | 11 | 11 | 14 | 15 |
| r9（換算。× 32/72 = 0.444） | 2.7 | 0 | 0.9 | 0.9 | 3.1 | 4.9 | 4.9 | 6.2 | 6.7 |

##### 理由3：落ちた点数は、最も測りたい区間の per-frame 指標を壊す

§32.5 により **可視点数 n < 5 のフレームは per-frame 指標として使えない。**

| 半径 | n < 5 のフレーム | 区間 |
|---|---|---|
| **6** | **2 フレーム** | index 42–43 |
| 9 | **13 フレーム** | index 34–46 |

index 34–46 は遮蔽からの再出現区間であり、**§12 の Control fidelity 項目
「遮蔽後の再出現位置」を測れる唯一の区間**である。r9 はその区間の
per-frame 指標を全損させる。Arm C を採る目的自体と衝突する。

##### 理由4：現在の Target 配置は r9 では幾何的に成立しない

| 項目 | 値 | 出所 |
|---|---|---|
| 円が重ならない最小中心間隔（半径 r） | 2r + 1.4142 | §13.4 / §28.3 |
| r6 の下限 | 13.4143 px | §13 |
| **r9 の下限** | **19.4142 px** | 上式 |
| **Scene C の達成分離（Target 帯 / 実測）** | **13.437 px** | §13 / §30 |
| Scene C の達成分離（背景 / 実測） | 20.898 px | 同上 |

**Target 帯の達成分離 13.437 px は r9 の下限 19.4142 px を下回る。**
つまり現在の Target 72 点の配置は r9 では作れない。

背景側の余裕も無い。**`armc_points.json` の実測（2026-08-06）で
`achieved_separation.background` = 20.8976 px を決めているのが
Marker の 2 点（id 80 / 81）であることを確認した。**

| 半径 | 非重なり下限 | Marker 2 点の実測分離 20.8976 px との比 |
|---|---|---|
| **6** | 13.4143 px | 1.558 倍 |
| 9 | 19.4142 px | **1.077 倍** |

**背景側の最小分離は最小の Entity（Marker、画面上 519 px / bbox 24×22）が決めている。**
r9 では Marker が制約の限界に張り付く。

##### 理由5：標本が小さく、r9 の優位そのものの確度が低い

§16.15-4 のとおり、r9 の採点対象は毎フレーム 73〜87 点で誤差は約 ±3.5 ポイント。
**r9 の優位は「小さい標本で測った、使われない余裕」である。**

##### 研究上の理由

Arm C の主張は「疎な追跡点でも密な Arm B に迫れるか」（§31）である。
r9 は占有率を変えずに**軌道の本数を 72 → 32 に半減させる**。Arm C が運ぶ情報は
点の軌道集合であり、色の頑健さではない。**表現の情報量を削って色を買う取引は
RQ の向きと逆である。**

##### この判断の根拠の性格（限界）

**r6 と r9 を Scene C で比較していない。** §16.11 は W1 の合成データ・
全画面占有率 12.8% での比較である。本節の根拠は Scene C での r9 実測ではなく、
**占有率という固定資源の配分の議論**である。

ただし §32.3 で「色誤差は局所占有率にほぼ依存せず速度でほぼ決まる」ことが
確定しており（r6 の W1 実測 11.30 に対し Scene C からの外挿 11.60、差 0.30）、
同じ理屈で r9 の 5.66 も Scene C へ移植可能と見るのが自然である。
その場合、理由1の余裕はさらに増えるだけで、結論は動かない。

##### 結論

**半径 6 px を維持する。r9 は採らない。** 変更しない。

### 22.1 Depth 規約

| 項目 | 値 |
|---|---|
| **Blender Depth パスの規約** | **A（Z-depth：カメラ平面からの垂直距離）** |
| 検証バージョン | Blender **5.2.0** / EEVEE（`BLENDER_EEVEE`） |
| 解像度 | 832 × 480 |
| Mist パス | **GT 用途では使用不可** |

```
A) Z-depth       カメラ平面からの垂直距離。光軸方向の成分のみ
B) Ray distance  カメラ原点から点までレイに沿った実距離（斜辺）

関係式  B = A / cos(θ)     θ = 光軸からの角度
画面中心（θ=0）では A = B。端に行くほど乖離する
```

**検証方法**：カメラに完全正対した平面を置き、Depth パスが全域で一定値を返すかを見る。

| 設定 | 値 |
|---|---|
| 平面 | size 20、原点 (0,0,0) |
| カメラ | (0,0,5)、rotation (0,0,0) |
| 焦点距離 / センサー | **18 mm / 36 mm**（検証専用。本編の50mmとは別） |
| 水平半画角 | 45.0° |

| 位置 | 実測 | 規約A の予想 | 規約B の予想 |
|---|---:|---:|---:|
| center | 5.0 | 5.0 | 5.0 |
| left | **5.0** | 5.0 | 7.071 |
| right | **5.0** | 5.0 | 7.071 |

**陽性対照。** 端の角度が45.0°あるため、規約Bなら7.071（差41%）が出るはずだった。
出ていないので「感度不足で見分けられなかった」可能性は排除される。

> 検証専用に短焦点（18mm）を選んだのは画角を広げて差を作るため。
> 本編の50mm（水平画角39.6°）で同じテストをすると端の角度が19.8°しかなく、
> 規約Bでも 5.31（差6%）にしかならず判別が難しい。

**Mist を除外する理由**：0〜1に正規化された霧の濃さで、Start / Depth 設定に依存する
相対値。絶対距離ではないため GT に使えない。

### 22.2 各 Arm と Depth の関係

| 対象 | 座標の出所に Depth を使うか | 作り方 | 規約の影響 |
|---|---|---|---|
| Arm A（Clay Previs） | **使わない** | クレイレンダーのみ | なし |
| Arm B（Dense World-XYZ） | **使わない** | **Position パス直接** | なし |
| Arm C（3D Tracking） | **使わない** | **`bpy` で頂点座標直接** | 遮蔽判定でのみ関与（§13.4） |
| VGGT 評価の GT | **使う** | Depth パス | **ここが本体** |

**Arm A に Depth を入れない理由**：Arm A の役割は「外観ベースの素朴な統制条件」。
Depth を足すと「外観 + 幾何」のハイブリッドになり、Arm B との差が説明できなくなる。
RQ1 で差が出ても外観由来か幾何由来か切り分け不能。
なお、クレイレンダーの陰影自体が法線由来の暗黙的な幾何情報を含んでおり、
明示的な Depth は二重取りにあたる。

**Arm B / C が逆投影を通らない理由**：どちらも Blender シーン内に正解の3D座標が
既に存在するため。EEVEE の Position パス（View Layer Properties → Passes → Data →
Position）で World 座標を直接出力できることを確認済み。

**副次的な利点**：逆投影を通さないことで、`fov` 由来のバグが Arm B に混入する経路が消えた。
fov 誤りと規約誤りは「画面端ほど座標がズレる」という同一の症状を示すため、
両方が同時に効きうる経路は減らすほど良い。

> ⚠️ **Arm C は順投影を通るので経路は完全には消えていない。** §13.4 を参照。

### マスクは `pass_index` で定義する（2026-08-04 確定）

**値の許容範囲でマスクを作ってはならない。** 隣接する別の面が漏れる。

W2a-1 の実例。壁（World Y = 2.0）のマスクを `|Y − 2.0| < 0.05` で作ったところ、
Y = 1.8〜2.0 のマーカー側面のうち Y ≥ 1.95 の帯（19画素）が壁として拾われた。

```
列 647 / 行 115-133 の19画素
world X = 2.3984（マーカーの −X 側面）/ world Y = 1.9795 / depth = 11.9798

Depth 規約は破れていない（`depth = Y + 10` が成立）。マスク定義の欠陥だった。

**規定。** Object Index パス（`view_layer.use_pass_object_index`）と
`object.pass_index` でマスクを定義する。`.blend` に焼いて保存する。

### 22.3 レンダラの選定

| 用途 | レンダラ | 理由 |
|---|---|---|
| Arm A（クレイ） | **EEVEE** | 高速・ノイズなし・GI 不要 |
| Position / Depth / Object ID / Visibility パス | **EEVEE** | Position パスの存在を確認済み |
| Target video | split に従う（§7） | **R0=EEVEE / R1=Cycles** |

**サンプル平均は幾何パスに使えない。** 1ピクセル内の複数サンプルを平均すると、
物体の輪郭に「手前と奥の中間値」＝実在しない座標が生成される。
輪郭は本研究で最も重要な領域であるため、これは許容できない。

**EEVEE も平均する（2026-08-04 訂正）。** rev.3 は Cycles 固有の問題として
書いていたが誤り。EEVEE も `taa_render_samples` 個のサンプルを平均し、
`filter_size` で画素間をぼかす。§22.1 の Depth 規約検証は平らな板を相手にしていたため、
平均しても値が変わらず見落としていた。

**幾何パスの必須設定。**

| 設定 | 値 | 既定値 |
|---|---|---|
| `scene.eevee.taa_render_samples` | **1** | 64 |
| `scene.render.filter_size` | **0.01** | 1.5 |

外観用（Arm A クレイ / Target video）は AA が色にしか効かないので既定値でよい。

| 用途 | taa_render_samples | filter_size |
|---|---|---|
| 幾何パス（Position / Depth / ObjIdx） | **1** | **0.01** |
| 外観（Arm A / Target video R0） | 64 | 1.5 |

**検証済み（W2a-1）。** 行240を走査し、合法値の集合（壁 2.0 / 遮蔽板 −3.0 /
Target 表面 [−0.5, 0.5]）から外れる画素が **0** であることを確認した。

やむを得ず幾何パスで Cycles を使う場合もサンプル数を1にする。

```

### 22.4 VGGT 側の規約（暫定）

| 項目 | 状態 |
|---|---|
| 推定される規約 | **A（Z-depth）** |
| 確度 | **強いが間接。コード未確認** |
| 実地検証 | **Day 25-31（VGGT 初回起動時）** §18-14 |

**根拠**：VGGT の README では、カメラヘッドの出力を OpenCV 規約の
extrinsic / intrinsic に変換し、`unproject_depth_map_to_point_map(depth_map,
extrinsic, intrinsic)` で3D点群を構成している。

intrinsic 行列 K を用いた逆投影の標準形は次の通り。

```
3D点 = z × K⁻¹ × (u, v, 1)
```

この `z` は光軸方向の成分であり、レイ距離を代入すると画面端で座標が破綻する。
**K を用いる実装は必然的に規約 A。**

**検証を遅らせる判断の理由**（「予測を信じる」ではなく「検証がタダになる時点まで遅らせる」）

### 移植用のヘルパ

```python
def iter_fcurves(obj):
    """旧構造と slotted actions の両方に対応する。"""
    ad = obj.animation_data
    if ad is None or ad.action is None:
        return []
    act = ad.action
    legacy = getattr(act, "fcurves", None)
    if legacy is not None:
        return list(legacy)
    out, slot = [], getattr(ad, "action_slot", None)
    for layer in act.layers:
        for strip in layer.strips:
            cb = None
            if slot is not None and hasattr(strip, "channelbag"):
                try:
                    cb = strip.channelbag(slot)
                except (TypeError, RuntimeError):
                    cb = None
            if cb is None and hasattr(strip, "channelbags"):
                bags = list(strip.channelbags)
                cb = bags[0] if bags else None
            if cb is not None:
                out.extend(cb.fcurves)
    return out
```

|---|---|---|

| 2 | **例外を捕まえて残りの検査を続行させる** | 1つの API 不一致で全レポートが失われるのを防ぐ |
| 3 | **出力パスを推測せず、実在するファイルを走査して拾う** | `frame_path()` と `write_still` の規則が違った |

**Arm B の Target 情報ゼロ区間 = index 36–40 = target video の完全遮蔽区間と同一。**
**Arm B だけが Target 情報を持つ非対称は index 35 と 41 の 2 フレームのみ。**

#### RQ2 に使う情報量の3段構造

7フレームの非対称という形では使えない。代わりに1シーンに3段の条件が内在している。

| 段 | 区間 | フレーム数 | 条件 |
|---|---|---|---|
| 1 | 0–34 / 42–48 | 42 | Arm B / C ともに Target 情報あり |
| **2** | **35 / 41** | **2** | **Arm C のみ欠損** |
| **3** | **36–40** | **5** | **Arm B / C が同一のゼロ条件** |

段 3 のほうが交絡が少ない。「情報量が異なる2表現の比較」ではなく
「**情報がゼロという同一条件で、周囲の密な場（Arm B）と点の identity（Arm C）の
どちらが時間補間を支えるか**」を問える。

**Arm A は Target ラベルを持たないため全区間で Target を特定できない**（§2 / §28）。
「Arm A は情報を持ち続ける」と書かないこと。

#### Arm B が Target 情報を持つ画素の総量

49 フレーム合計の Target 帯の画素数は **621,437**（実測）。frame 0 単独が 27,669 で、
遮蔽が無ければ 49 × 27,669 = 1,355,781 になるはずなので **45.8%** しかない。
index 36–40 の完全ゼロだけでなく、前後で段階的に削られている
（`armc_points.json` の可視点数 72 → 6 → 0 → 15 と同じ形）。

`render_arm_c.py` の `fully_occluded_*` 検査は「36–40 で Target 色が出ないこと」しか
見ていないため、35 と 41 が 0 であることは検出されなかった。

### 正規化ボックス（Arm B。§18-4 の Scene-bounded を固定値で与える）

## 27. 幾何パスの実装規約（W2b Step 3 の実測）

### 27.1 コンポジタの配線 — **ここを間違えると無言で壊れる**

```
RLayers.<socket> -> NodeGroupOutput
  ng.interface.new_socket(name=..., in_out="OUTPUT", socket_type="NodeSocketColor")
```

**出力インターフェースのソケット型は必ず `NodeSocketColor`。**

| 経路 | `is_valid` | 出力 |
|---|---|---|
| **NodeSocketColor** | True | ✅ 正しい値 |
| NodeSocketVector（Position は VECTOR 型） | **True** | ❌ Combined |
| NodeSocketFloat（Depth は VALUE 型） | **True** | ❌ Combined |
| `interface.new_socket` を呼ばず仮想ソケットへリンク | False | ❌ Combined |

**型を合わせると失敗する。**そして失敗しても例外も警告も出ず、
コンポジタが無視されて Combined がそのまま書かれる。

**この故障は一意値の個数でも値域でもファイルサイズでも検出できない。**
既知座標の画素値を手計算と突合する以外に検出手段がない（§30.1 の照合点）。

### 27.2 `view_transform` について（rev.5 の記述を撤回）

rev.5 で「AgX が Position を圧縮する。Raw が必須」と書いたが**誤り**。
あの [0, 0.475] は配線ミスで出た Combined の線形値で、view_transform とは無関係だった。

実測（Arm A のコンポジタ無し経路）では **Standard / Khronos PBR Neutral / AgX の
3つでバイト単位に同一**、かつ energy 3倍で値も厳密に3倍。
**EXR 出力にトーンマップはかからない。値は線形で出る。**

幾何パスはコンポジタ経由で経路が違うため未検証。`Raw` の設定は残すが必須条件ではない。

### 27.3 マスクは Emission ID レンダーで作る（§14 の変更）

**EEVEE に Object Index パスは存在しない。**
`view_layer.use_pass_object_index = True` は代入に成功して True を返すが、
RLayers の出力ソケットは Image / Alpha / Depth / Mist / Normal / Position の6本のみ。

```
全オブジェクトを Emission に差し替え、Strength = pass_index、Color = 白
film_transparent = True / World の Strength = 0
RLayers.Image -> NodeSocketColor
```

32bit EXR に **pass_index の値が厳密に保存される**（実測：1.0 / 4.0 が誤差 0 で復元）。
`Color` に pass_index を入れてもクランプされないが、意味が明確な `Strength` を使う。

### 27.4 EEVEE の設定名

| 項目 | 正しい属性 |
|---|---|
| サンプル | `scene.eevee.taa_render_samples` |
| フィルタ | `scene.render.filter_size`（既定 1.5。幾何パスは 0.01） |
| モーションブラー | `scene.render.use_motion_blur`。**`scene.eevee.use_motion_blur` は存在しない** |
| レイトレース | `scene.eevee.use_raytracing`（既定 False） |
| ボリューム光 | `use_volumetric_lights` は存在しない |

**EEVEE Next は `use_raytracing = False` だと World が面の陰影に寄与しない。**
World の Strength を変えても結果が変わらない（実測で 0.10 と 0.50 が完全一致）。

### 27.5 Cycles は使える（enum が嘘をつく）

`scene.render.bl_rna.properties["engine"].enum_items` は `['BLENDER_EEVEE']` しか返さず、
`bpy.types.CyclesRender` も False。**しかし `scene.render.engine = "CYCLES"` の直接代入は成功する。**

同じ症状が `view_transform` でも出た（enum は `['NONE']` を返すが既定は AgX で
Standard / Khronos PBR Neutral / AgX / Filmic / False Color / Raw がすべて代入可能）。

**enum の内省を信用しない。直接代入して確かめる（作法#16）。**

### 28.3 Arm C（Object-Aware 3D Tracking）

| 項目 | 値 |
|---|---|
| 候補点 | **面上の 0.10 ピッチ格子**（頂点そのままではない） |
| **格子の生成** | `floor(ext/pitch + 1e-4)`。**mathutils.Vector は float32 で誤差 1e-6。1e-9 では効かない** |
| 点集合と色 | **両変種で共有。**選定・彩色は Original 49f + Edited 49f = 98 フレームの和で行う |
| 軌道の与え方 | `.blend` の fcurve ではなく KEYFRAMES から直接（5.2 の layered fcurve API に依存させない） |
| 選定方式 | **最遠点サンプリング。点数が入力、達成分離が出力** |
| 点数 | **240**（Target 72 / Non-target 168 = 割合 0.3000） |
| Entity quota | **DeepObject 8 / Occluder 8 / Marker 2** を先に確保してから残りを配る |
| 分離の下限 | **13.4143 px**（下記） |
| 彩色 | 次数の大きい順に貪欲。**許される色のうち使用回数が最小のものを選ぶ** |
| 可視判定 | `scene.ray_cast`（eps 1e-3）。**正面性フィルタは入れない**（§13.4 / §18-19） |
| 描画 | 中心を最近画素中心に丸め、`dx²+dy² ≤ 36` で 113 px。深度の遠い順 |

#### 円の重なり閾値の訂正（rev.5 の「12 px」は誤り）

| 整数中心の距離 | 共有画素 |
|---|---|
| 11 px | 2 |
| **12 px** | **1** |
| 13 px | 0 |

連続座標を整数に丸めると距離は最大 1.4142 px 縮む。
**重なりを保証で無くすには連続分離 > 13.4143 px。**
実測の達成分離 13.437 px で重なり画素は **98フレーム合計 0**。

#### 「点数を入力・分離を出力」にする理由

面積が固定なので d を入力にすると点数が決まってしまい、
protocol の「Target 点の割合 0.30」を満たせない。点数を固定し、
最遠点サンプリングで分離を最大化し、達成値が下限を超えることを検査する。

#### 彩色を均等化する理由

背景点は 24px 以内に一度も接近しないため衝突ペアが 0〜1 本しかない。
最小インデックスの空き色を選ぶ素朴な貪欲彩色だと**全点が color 0** になり、
identity 復元率が原理的に測れなくなる。使用回数最小を選べば局所分離の保証は
変わらないままパレットを均等に使える（実測：両帯とも 12/12 色、6点/14点ずつ）。

| マスク後（全体） | 前4条件を満たす | 8,809,739 | 画面の 95.91% |
| **far** | Target シルエットから 2px より外 | 8,784,521 | 99.71% |
| **near** | Target シルエットから 2px 以内 | 25,218 | 0.29% |

### far 群の |Δ|max の分布（1フレームあたり）

| 帯 | 画素/フレーム | far 全体比 | 正体 |
|---|---|---|---|
| Δ = 0 | 379,571 | 99.381% | 何も起きていない |
| Δ = 1–2 | 102 | 0.027% | 8bit 丸めのジッタ |
| Δ = 3–128 | 1,161 | 0.304% | **半影の連続分布** |
| **Δ = 129–135** | **1,102** | **0.289%** | **影のコア（明 → 真っ黒）** |
| Δ ≥ 136 | 0 | 0% | 存在しない |

**Δ = 135 でぴったり切れる**ことが機序の証拠。`use_raytracing = False` では World が
陰影に寄与しない（§27.4）ため、影に入った画素は環境光ゼロで 0 に落ちる。
したがって Δ の上限 = 影を受ける面の照明値そのままになる。

`far` の空区間（谷の候補）は **136–254 のみ**。**3–128 に谷は存在しない。**
半影は連続量なので原理的に谷が出ない。

### 許容値の感度（これが確定の根拠）

| 許容値 | M_invariant（far のみ） | 画面比 |
|---|---|---|
| 0 | 379,571 px/frame | 95.045% |
| 1 | 379,649 | 95.064% |
| **2** | **379,673** | **95.070%** |
| 8 | 379,757 | 95.091% |
| 16 | 379,828 | 95.109% |
| 24 | 379,874 | 95.121% |
| 32 | 379,926 | 95.134% |

**0 → 32 で 355 px/frame、画面の 0.089% しか動かない。** 分布が両端に寄っている
（中間帯 3–128 が合計 1,161 px/frame しかない）ため、閾値をどこに置いても結果が
変わらない。**論文にはこの表を robustness として載せる。**

### near 群を閾値ではなく幾何で落とす理由

| 群 | 画素/フレーム | Δ=0 の割合 |
|---|---|---|
| far | 381,936 | **99.38%** |
| near | 1,096 | **61.10%** |

near は far の **64 倍**汚れている。原因は AA の非対称で、**幾何パスは
`filter_size = 0.01` / `taa 1` だが target video は既定 1.5**（§22.3 / §29）。
Target シルエット際の画素は幾何マスク上は「床」と判定されるのに、tv 側では
Target と床の混色になっている。

これを閾値で殺すと許容値を 135 まで上げる話になり本末転倒。**幾何的に落とすのが
正しい。** コストは 1,096 px/frame = 画面の 0.275%。

### 確定した M_invariant

```
許容値 2（8bit / RGB の max）+ Target 近傍 2px 除外
→ M_invariant ≈ 379,673 px/frame = 画面の 95.07%
```

| # | 作法 | 由来 |
|---|---|---|
| **16** | **enum の内省を信用しない。直接代入して確かめる** | `view_transform` が `['NONE']`、`engine` が `['BLENDER_EEVEE']` しか返さない。どちらも実際には他の値を代入できる |

| **19** | **補間はプリファレンスでなく fcurve で決まる** | `keyframe_new_interpolation_type = "LINEAR"` は代入に成功するが `keyframe_insert` に反映されない。fcurve の `keyframe_points` を明示的に書き換える必要がある |

| **22** | **リテラルを丸めて凍結したら、突合の許容値をその丸め幅に合わせる** | 軌道リテラルを `%+.7f` で丸めたのに `1e-9` で突合して偽 FAIL を出した |
| **23** | **`open()` には必ず `encoding="utf-8"` を書く** | Python 3.11+ の既定はロケール依存。Windows（cp932）と RunPod（utf-8）で挙動が変わる。日本語を含む JSON を読むと `UnicodeDecodeError`、さらに悪いことに cp932 で解釈できる範囲なら**無言で別の文字として読める**。子プロセスの stdout も `PYTHONIOENCODING=utf-8` で固定する |
| **24** | **PowerShell の `Compress-Archive` を使わない** | パス区切りにバックスラッシュを書くため、Linux で展開すると `edited\\armC_0000.png` という1個のファイル名になりディレクトリ構造が消える。**zip の md5 は一致するので転送検証では検出できない。** 代わりに `python -c "import shutil;shutil.make_archive(...)"` を使う |

### 検出できない故障の型

W2b / W2c で「エラーも警告も出さずに間違った出力を出す」経路が3つ見つかった。

| 故障 | 検出手段 |
|---|---|
| コンポジタのソケット型が違い Combined が書かれる | **既知座標の画素値を手計算と突合する以外にない**（一意値の個数・値域・ファイルサイズでは不可） |
| `floor` が float32 誤差で格子を1行落とす | オブジェクトごとの候補点数を面ごとに出す |
| `matrix_world` の遅延評価 | 既知点の投影値を照合表と突合する |

**共通するのは「出力がもっともらしく見える」こと。** 閉形式で出した照合値との
突合を必ず入れる。

### 33.3 (a) Edited を train に入れない理由

|---|---|---|
| Spatial spillover が測るもの | control 追従の副作用 | 再生の忠実度 |
| 3 arm の差 | 表現の性質 | ほぼ消える |
| §15 の帰結 | 比較が成立 | **Arm間差 ≤ Pipeline floor → 主張不可** |

3 arm は target video を共有する（§7：Geometry / Animation / Object identity は
全 split 共通）。したがって**暗記経路は 3 arm で同一であり、arm 非依存の床として
働く。** RQ2 が測れなくなるだけでなく、Claim Gate に落ちて「差が無い」という
結論が出る。

加えて §10 は編集を反実仮想（counterfactual）と呼んでいる。**反実仮想は
観測していないものを指す語であり、train に入れた時点で定義に反する。**

**Edited target video（`tv\R0S0\edited\`）の用途は評価GTである。** M_invariant 上の
LPIPS / PSNR / SSIM を計算する参照であり、学習ターゲットではない。

> **罠として記録する。** この構成では train が N=1 サンプル（49フレーム1本）になる。
> ここで「Edited を足せば 2 本になる」という発想が出るが、それは RQ2 の反実仮想を
> 破壊する。**サンプル数を増やす正しい方法は Scene C′ 型の軌道変種を足すことである。**

### 33.4 (b) IID テストに Scene C′ が必要な理由

train の control 上で閾値（§12 の T_control / T_coherence）を測ると、
**モデルは control を読まずに閾値を満たせる。**

| 経路 | control を読む必要 | arm 間で差が出るか |
|---|---|---|
| control 追従で Target を動かす | あり | 出る（これが RQ1） |
| 学習動画の画素を暗記して再生 | **なし** | **出ない** |

**Scene C′ は主張範囲を広げるためではなく、RQ1 に信号を残すために必要である。**
held-out control が無ければ「表現が吸収された」と「出力が暗記された」を
区別できず、暗記経路は 3 arm で同一なので arm 差が消える。

#### Scene C′ の仕様

| 項目 | 値 |
|---|---|
| 変種 | **Original のみ**（Edited を持たない。RQ2 は既存 Scene C で行う） |
| split | **R0S0 のみ**（R1S0 / R0S1 は 9月） |
| 生成物 | geo / armA / armB / armC / tv 各 49 枚 |
| 点集合・色 | **Scene C と共有する。選び直さない** |
| カメラ / 光源 / 材質 / Entity 配置 / 幾何 | **Scene C と同一** |
| 差し替えるもの | **Target 軌道のみ** |

点集合を共有する理由は W2 の決定 #2 と同じ。**選び直すと IID テストが
「新しい軌道」と「新しい点集合」を同時に変えることになり、何を測ったのか
分離できなくなる。**

**既存の Scene C とその Edited、882 ファイル、M_invariant（95.07%）、
Arm C の 240 点は一切変更しない。** Scene C′ は純粋な追加である。

占有率が 30% を超える。** 点集合は共有するため点数を減らせない。

制約 3 の理由は §33.11（参照画像）にある。

### 33.5 (c) 遮蔽なし条件を train に入れない理由

| train の中身 | モデルが学ぶこと |
|---|---|
| 遮蔽ありのみ | 「Arm C の点が消えたら Target は遮蔽物の裏」という事前分布 |
| 遮蔽あり + なし | 上の事前分布が効かなくなる |

noocc を train に入れると Arm C の遮蔽時情報損失に対する補償が弱まる。
**それは表現の性質ではなく学習データ構成の効果であり、** RQ2 の主張が
「Arm C は遮蔽に弱い」から「Arm C は遮蔽なしデータで学習すると遮蔽に弱い」へ
劣化する。加えて (a) と同じ暗記経路の問題も生じる。

**Scene C-noocc の生成は Phase 0.8 の偵察 run（§33.7）の後に行う。**
偵察 run で C′ 上の Control fidelity が 3 arm ともに T_control を下回る場合、
遮蔽対照は成立しないため生成しない。

### 33.6 (d) step と epoch の定義

**「500 steps」は optimizer step 数を指す。** grad accum を含む micro-batch
回数ではない。

**ただし DiffSynth に steps を指定するフラグは存在しない**（2026-08-07 実装確認。§35.2）。
指定するのは `--num_epochs` であり、steps は結果として決まる。下式は向きを逆に読む。

| 記号 | 意味 |
|---|---|
| N | train の動画本数 |
| B | batch size |
| A | gradient accumulation |

```
1 optimizer step で消費するサンプル数 = B × A
500 steps で消費する総サンプル数      = 500 × B × A
epoch 数                             = 500 × B × A / N
```

N=1 / B=1 / A=1 の初期構成では **500 epoch**。同じ 49 フレームを最低 500 回見る。
これが §33.4 の暗記経路が現実的な懸念である根拠。

**この二択の立て方は誤りだった（§35.2 で訂正）。** 学習量のフラグは `--num_epochs` で
あり step ではない。micro-batch で数えるのは `--save_steps`（チェックポイント間隔）で
あって学習量ではない。**A>1 にすると `step-*.safetensors` のファイル名が
optimizer step と A 倍ずれる**点だけが残る実害である（§35.4）。
**`examples/train.py` が独自に引数を追加していないかは 20-step スモークで確認する。**

**B と A は N が確定するまで決めない。** N=1 では B≥2 は同じ動画を 1 step で
複数回見るだけであり意味を持たない。§8 の 29.4 GB は B=1 の実測値であり、
**activation は B に線形、モデル重みと optimizer state は B に不変なので
線形外挿しない。**

### 33.11 参照画像の扱い（§18-13。2026-08-06 確定）

#### 決定

**`vace_reference_image` には、そのシーンの target video の frame 0 を渡す（案 13-B）。**
DiffSynth 公式サンプルと同一の構成である。

#### §18-13 は交絡要因ではなかった

rev.7 の §8 は「3 arm でどう揃えるかは未決定。RQ1 の交絡要因」と記していた。
しかし**参照画像は target video から取るものであり、target video は 3 arm で
共有される**（§7：Geometry / Animation / Object identity は全 split 共通）。
したがって公式構成に従えば**参照画像は 3 arm で bit 一致し、揃えるかどうかの
問題は発生しない。**

交絡が生じるのは 1 つの場合だけである。

| 案 | 参照画像の出所 | 3 arm で | 判定 |
|---|---|---|---|
| 13-A | 参照画像を使わない | 同一（無い） | 可 |
| **13-B** | **各 Scene の target video の frame 0** | **同一** | **採用** |
| 13-C | 各 arm の control video の frame 0 | **arm ごとに異なる** | **却下** |
| 13-D | Target を隠した静止参照を 1 枚作り全 Scene で共有 | 同一 | 可 |

**13-C は却下する。** Arm A にクレイ画像、Arm B に XYZ 色、Arm C に点画像を
参照として渡すことになり、arm 固有の外観情報が直接注入される。参照画像は
target ドメインの画像であるべきという前提にも反する。

#### 13-B を採る理由

**理由1：参照画像が代行するのは appearance であり、control の仕事である
structure ではない。**

| 参照画像が供給するもの | RQ1 への効果 |
|---|---|
| 見た目 / スタイル / 静止物の配置 | **正。** style 学習の負担が消え、残る学習が control 読解に絞られて arm 差が鋭くなる |
| Target の初期位置 | 負。軌道の始点は control が指定すべき情報 |

§33.3・§33.4 で用いた「共有情報は arm 非依存の床になる」という論法は、
ここでは逆向きに働く。**appearance を無料で渡すと、500 steps という限られた予算の
うち control 読解に使える割合が増える。**

**理由2：13-A は 500 steps で全 arm 失敗するリスクが高い。** style と control を
同時に学ばせる構成になり、§33.7 の予測（暗記に落ちる）と重なる。

**理由3：13-D は未測定のリスクを無償で背負う。** 参照フレームに Target が
写っていない状態を学習し、冒頭フレームから Target が消える恐れがある。
13-B に制約を 1 本足せば同じ性質が無償で得られる（下記）。

#### C′ の制約 3 との関係

**Scene C′ の Target 開始位置を Scene C と同一にする**（§33.4 の制約 3）ことで、
C′ は幾何・カメラ・光源・材質・Entity 配置を Scene C と共有しているため
**`tv` の frame 0 が Scene C と bit 一致する。**

| 制約 3 なし | 制約 3 あり |
|---|---|
| C と C′ で参照画像が異なり、C′ の初期位置が漏れる | **参照画像が 1 枚に collapse し、漏れる情報が train / test で同一になる** |

**新規レンダーなしで 13-D と同じ性質が得られる。** 漏れるのは全条件で共通の
1 枚のみとなり、IID テストの独立性を侵さない。

#### 前提の実測確認（2026-08-06）

13-B は「target video の frame 0 に Target が写っている」ことを前提とする。
**Target が画面外から進入する設計であればこの前提は崩れ、13-D と同じリスクを負う。**

| 確認項目 | 結果 |
|---|---|
| frame 0 の Target 可視点数 | **72 / 72 すべて `visible` = True** |
| Target の画面面積（実測） | 28,029 px |
| 閉形式での予測 | 27,673 px（差 +1.29%） |
| Target の同定 | オレンジの六角柱（`object` = `Target`、`pass_index` = 3） |

**前提は成立している。** 詳細は §33.4 の実測表。

#### 残る限界（Limitations に記載する）

**参照画像は Target の初期位置を漏らす。** ただし

1. 全 arm・全 Scene で同一の 1 枚である（制約 3 により）
2. 漏れるのは 49 フレームのうち 1 フレーム分の始点のみである
3. §12 の Control fidelity が主に測るのは軌道誤差 / 最終位置誤差 /
   遮蔽後の再出現位置であり、始点ではない

**それでも「初期位置は control ではなく参照画像から与えられている」ことは
明記する。**

#### 実装上の注意（未検証。§18-26）

**参照画像は時間方向に前置きされる。** 参照フレームがマスクされないよう
ゼロマスクも前置きされる。1 枚の参照画像は 1 latent フレーム
（= 4 ピクセルフレーム相当）を消費する。

| | 参照なし | 参照あり |
|---|---|---|
| denoising 側の latent 時間長 | 13 | **14 で走り、後から 13 に切る** |
| vace_context の latent 時間長 | 13 | **14** |

**この表は rev.8 で「denoising 側は 13 のまま」と書いていたが誤りだった。**
推論パスでは `noise` が 14 で生成され（`wan_video.py:384-387`）、denoising 後に
`latents[:, :, f:]` で先頭 1 枚を切る（`wan_video.py:344`）。2026-08-07 訂正。§35.6

**§8 の VRAM は参照画像ありで 30,109 MiB と実測された**（2026-08-09。W0 の 1-step 実行と完全一致）。§36.8

なお `vace_video` / `vace_video_mask` / `vace_reference_image` を同時に指定した
場合の shape エラーが上流で報告されている。**本設計は `vace_video_mask` を
使わない**（§8 の `extra_inputs` は `vace_video, vace_reference_image` のみ）ため
該当しないが、スモークで確認する。

### 34.2 判断の根拠：2種類の誤差

| 誤差の種類 | ボックス倍率 k に依存するか |
|---|---|
| 量子化（`rint` の丸め残差。最悪 0.5 LSB + 系統 0.25 LSB） | **する。厳密に線形** |
| VAE 往復の 8bit 誤差 ε | **する。ただし単調でない** |
| band confusion / 予約帯 | **する。k を上げると減る**（34.4） |

**混ぜてはいけない**（§11 と同じ理由）。§18-4 が問うのは前2者。

### 35.2 学習ループは epoch 駆動であり `--num_steps` は存在しない

`parsers.py` の学習系引数に `--num_steps` / `--max_steps` / `--max_train_steps` は無い。
`runner.py:78` は `for epoch_id in range(num_epochs)` であり、内側が dataloader の
全走である。

| フラグ | 意味 |
|---|---|
| `--num_epochs` | **学習の総量を決める唯一のフラグ**（既定 1） |
| `--dataset_repeat` | 1 epoch 内でデータセットを繰り返す回数（既定 1） |
| `--gradient_accumulation_steps` | Accelerator へ渡す A（既定 1） |
| `--save_steps` | チェックポイント間隔。**None なら epoch ごとに保存** |

したがって §33.6 の式は向きが逆だった。**steps を指定して epoch が出るのではなく、
epoch を指定して steps が出る。**

```
micro-batch 回数  = num_epochs × dataset_repeat × N
optimizer step 数 = micro-batch 回数 / A
```

N=1 / A=1 / `dataset_repeat`=1 の初期構成では **`--num_epochs 500` が 500 optimizer steps**。

### 35.3 batch size はフラグではない（B=1 が実装で固定）

`runner.py:66`。

| 事実 | 根拠 |
|---|---|
| `--batch_size` フラグが存在しない | `parsers.py` に無い |
| DataLoader が `batch_size` 未指定 | 既定 1 |
| `collate_fn=lambda x: x[0]` | サンプル 1 件を取り出して剥がす。**B≥2 を渡すと崩れる形** |

**実効バッチを上げる手段は `--gradient_accumulation_steps` のみ**
（`--dataset_repeat` は epoch 内の反復であり実効バッチではない）。
§18-2 の「batch size をどう決めるか」は決定対象ではなくなった。

### 35.4 step カウンタは micro-batch で数える

`logger.py:78-88`。`on_step_end` は `runner.py:91` で呼ばれ、その位置は

| 事実 | 帰結 |
|---|---|

| 渡し方 | 結果 |
|---|---|
| PNG パスの list | `ValueError`。**落ちるので安全** |
| **PNG 1 枚のパス** | `LoadImage >> ImageCropAndResize >> ToList()` → **1 フレームの list** |

**後者はエラーも警告も出さない。** `vace_video` に `armB_0000.png` を書くと
49 フレームのうち 1 フレームだけで学習が回り、loss も下がる。
**§17 の「エラーを出さずに間違った出力を出す」経路の 8 本目として記録する。**

### 36.3 非可逆エンコードは Arm B の codebook を破壊する

Arm B の量子化予算は 0.044118 units = 7.043 px（1 LSB の半分。§34.2）。
合成データ（帯の端の値 13 / 15 / 124 / 127 / 128 / 131 を含み、半径 6 の円板を
配置したもの）で 3 方式を比較した。

| エンコード | bit 一致 | 最大絶対差 | 不一致画素 |
|---|---|---|---|
| **FFV1 gbrp** | **True** | **0** | **0** |
| H.264 yuv420p（既定） | False | 180 | 19,406,737 |
| H.264 crf0 **yuv444p** | False | 2 | 16,524,430 |

**crf 0 でも可逆ではない。** yuv444p は数学的に可逆だが RGB→YUV→RGB の丸めが
非可逆であり、**全画素の 39.5% が ±1 ずれる。**

| 誤差 | 割合（crf0 yuv444p） |
|---|---|
| 0 | 60.37% |
| **1** | **39.50%** |
| 2 | 0.13% |

**±1 LSB は Arm B の量子化予算の 2 倍**であり、座標が最大 14 px 動く。
しかも VAE 往復誤差の p95 = 2.0（§34.3）と同じオーダーなので、
**ε の測定結果と区別がつかない。**

H.264 既定での最初の不一致は `PNG=[13,13,13] → mkv=[12,12,12]`。
**帯の下端 13 に張り付いた。** Arm B の min は 15（床の Z=−1.50）で帯の下端に
近いため（§34.3）、まさにそこが潰れる。

### 36.4 採用するエンコード

```
ffmpeg -y -fflags +bitexact -f rawvideo -pix_fmt rgb24 -s 832x480 -r 16 -i pipe:0 \
       -c:v ffv1 -level 3 -pix_fmt gbrp -g 1 -flags +bitexact -fflags +bitexact out.mkv
```

| フラグ | 理由 |
|---|---|
| `-c:v ffv1 -pix_fmt gbrp` | RGB のまま可逆。YUV 変換を通らない |
| `-g 1` | 全フレーム intra。`reader.get_data(i)` の単体取得が確実になる |
| `-flags +bitexact` / `-fflags +bitexact` | **同一入力で同一ファイルになる。** 付けないと Matroska が SegmentUID と DateUTC を書き込み、同じ PNG から作っても sha256 が毎回変わる |
| `-r 16` | `LoadVideo` が `get_meta_data()['fps']` を読むため値が必要。`fix_frame_rate=False` なのでフレームは 1:1 で取られ、内容には影響しない |

**ファイルのハッシュは ffmpeg のバージョンに依存するため環境をまたいだ照合には
使えない。** デコード後の画素のハッシュ（**content sha256**）を照合値とする。

## 37. 絶対閾値の定義（§18-6 / §18-27 / §33.10。2026-08-09 確定）

### 37.1 rev.9 までのゲートは型として成立していなかった

§12 は関門をこう書いていた。

```
Control fidelity ≥ T_control  AND  State coherence ≥ T_coherence
```

しかし中身はスカラーではない。

| | §12 の定義 | 型 |
|---|---|---|
| Control fidelity | 軌道誤差 / 最終位置誤差 / 移動方向 / 速度 / Mask IoU / 遮蔽後の再出現位置 / 軌跡連続性 | **7 指標。単位が px・比率・度で混在** |
| State coherence | 対象数 / 複製 / 消失 / フリッカー / 形状崩壊 / Track 切断 / テレポート / ID switch / identity 混同 / 遮蔽後の再取得 / 判定不能 / Tracker failure | **12 項目の破綻カウント** |

さらに**不等号の向きが誤っていた。** 軌道誤差は小さいほど良いので `≤` である。
IoU は大きいほど良いので `≥` である。**混在したまま 1 本の不等式で書かれていた。**

**§18-6 が長く未決だった原因はここにある。** 数値を決める前に、7 指標をどう扱うかが
決まっていなかった。

### 37.2 決定：代表 1 指標をゲートにし、残りは報告のみ（案 6-C）

| 案 | 内容 | 判定 |
|---|---|---|
| 6-A | 7 指標を重み付けして合成スカラー 1 本を作る | **却下** |
| 6-B | 7 指標すべてに個別の閾値を置き、全通過を要求 | 却下 |
| **6-C** | **代表 1 指標をゲートにし、残り 6 指標は報告のみ** | **採用** |

**6-A を却下する理由 1：§15 の Claim Gate が指標ごとの比較を要求している。**
Claim Gate は `Arm 間差 ≤ Evaluator floor` / `≤ Pipeline floor` の形であり、
**床は指標ごとに違う値である。** 合成スカラーにすると床と比較できず、§15 と両立しない。

**理由 2：RQ2 は「どこに漏れたか」を問う設計である。** 合成するとどの指標で差が
出たかが消える。情報を捨てる方向である。

**理由 3：§11 の「指標を混ぜてはいけない」と正面衝突する。** 重みが恣意的であり、
その重みが結論を動かす。

**6-B を却下する理由：** 閾値を 7 本、根拠付きで今月中に決めることはできない。
また AND を取ると全 arm が落ちて関門として機能しない。

**関門は「良いか」ではなく「そもそも使い物になっているか」を判定するものである。**
関門を 7 本にする必要はない。

### 37.3 代表指標：Target center trajectory error

| 候補 | 採否 | 理由 |
|---|---|---|
| **Target center trajectory error（px）** | **採用** | §12 の筆頭。制御性能そのもの。px 単位なので Target の画面サイズで根拠付けできる |
| Target Mask IoU | 却下 | 形状崩壊（State coherence 側）が混入する。制御だけを測れない |
| 最終位置誤差 | 却下 | 1 フレームなので分散が大きい。軌道誤差の部分集合 |
| 遮蔽後の再出現位置 | 却下 | 測れるフレームが数枚しかない（§16.16）。ゲートには薄い |

### 37.4 集計面（§33.10 の具体化）

**動画は Scene C′（IID）を主とする**（§33.10 で既決）。
本節ではフレーム集合と統計量を確定する。

**Target が GT で見えないフレームでは中心誤差が定義できない。**

| 区間 | フレーム | 扱い |
|---|---|---|
| GT で Target 可視 | **0–35 / 41–48 = 44 フレーム** | **主集計** |
| 完全遮蔽 | 36–40 = 5 フレーム | **別枠。** 誤差ではなく「消えているべき」の有無を検査 |
| 再出現直後 | 41–44 | 別枠で §12 の「遮蔽後の再出現位置」として報告 |

区間の根拠は §26 の訂正（Arm B の ID パスに `pass_index` 3 が存在するフレーム）。

**統計量は median（p50）を主、p95 を副とする。**
検出器の失敗フレームが max を支配するため、平均も max も使えない。

### 37.5 T_control = 47 px

**median 中心誤差 ≤ 47 px。**

根拠は Target の画面サイズである。

| 錨 | 値 | 出所 |
|---|---|---|
| Target の画面面積 | 28,029 px | §33.4 実測 |
| **等価円半径** | **94.5 px** | √(28029/π) |
| 画面 | 832 × 480 = 399,360 px | §5 |
| Target の画面占有 | 7.0% | |

**47 px は等価半径の 50% である。** 円板近似で中心が半径の半分ずれたときの
重なりを計算すると次のようになる。

| d / r | IoU |
|---|---|
| 0.25 | 0.72 |
| **0.50** | **0.52** |
| 0.75 | 0.35 |
| 1.00 | 0.22 |

**「半分以上重なっている」が Absolute usability の下限である。**
C′ の速度制約（≤ 12 px/frame。§33.4 制約 1）で換算すると
47 px ≈ **3.9 フレーム分の移動量**であり、
「軌道の形は追えているが位相が 4 フレームずれている」あたりが境界になる。

**速度基準（≤ 12 px = 1 フレーム分）を採らない。** それは「良い制御」の基準であり
関門としては厳しすぎる。500 steps で全 arm が落ちると関門として機能しない
（落ちたことしか分からない）。

### 37.6 T_coherence = 2 / 44

代表指標は **Target の検出個数**とする。12 項目のうち「対象数 / 複製 / 消失」が
同一の測定（個数 ≠ 1）であり、検出器の出力から直接得られる。

**個数 ≠ 1 のフレームが ≤ 2 / 44（4.5%）。**

「2」は恣意的な数ではない。**幾何的に判定が難しいフレーム数と同じ本数である。**
§26 の訂正で frame 35 と 41 は Arm B に `pass_index` 3 があるのに Arm C の
可視点が 0 という部分遮蔽フレームだと確定している。**そこで個数を外すのは
表現の問題ではなく遮蔽の問題**であるため、その本数だけを予算として認める。

**Tracker failure は分母から外して別カウントする**（§12 の
「自動検出器の失敗と、生成映像そのものの破綻を分離して記録する」に従う）。

### 37.8 保険条項（Evaluator floor が閾値を超えた場合）

**T_control を先に決めたが、Evaluator floor（§15 / §18-9）は未測定である。**
検出器自体の中心誤差 p95 が 47 px を超えていれば、この関門は検出器の性能を
測っているだけになる。

| 条件 | 対応 |
|---|---|
| Evaluator floor の p95 < 47 px | 47 px を関門として使う |
| **Evaluator floor の p95 ≥ 47 px** | **関門を撤回し、floor をそのまま報告する** |

後者の場合は「今月は絶対閾値では判定不能」と記述する。
**閾値を測定後に緩めることは事後合わせであり禁止する。**

### 37.9 §18-27 の決定：座標誤差と band violation を分離する（案 27-B）

**§18-27 は §18-6 と依存していなかった。** rev.8 が「§18-6 と同時に決める」と
書いていたのは事務上の都合である。

| | 指標の家族 | 節 |
|---|---|---|
| §18-6（T_control） | 生成映像の評価 | §12 |
| §18-27（帯反転） | Control が VAE を生き延びるか | §13・§16 |

§12 の冒頭が「2 つを混同しない」と明記している。

#### 数値で選択肢が潰れた

帯反転 251 px（§34.4）が座標誤差の集計に与える影響を計算した。

| 統計量 | k=1 の実測 | 帯反転の影響 |
|---|---|---|
| mean | 0.5146 | −0.36%（251 × 145.5 ÷ 19,568,640） |
| p50 | 0.0 | **ゼロ**（251 px = 1.28e−5。p99.999 より外） |
| p95 | 2.0 | **ゼロ** |
| p99 | 3.0 | **ゼロ** |
| **max** | **146** | **100%。max はこれしか測っていない** |

**max 以外は帯反転に影響されない。** 除外するか否かで悩む必要はなく、
決めるべきは「max を報告指標に使うか」だった。

#### 決定

| # | 項目 | 決定 |
|---|---|---|
| 1 | 座標誤差の報告統計量 | **median / p95 / p99。max は使わない** |
| 2 | 集計母集団 | **全画素。帯で選別しない** |
| 3 | 帯違反 | **独立指標として画素率（ppm）で別報告。予約帯と帯反転を分けてカウント** |

**2 が重要である。** 帯が正しい画素だけを選ぶには `armb_decode.classify` が
必要だが、**あの関数には構造上発火しない assert が 1 本ある**
（`tie.min() == 3` は常に真）。分位点なら選別が不要であり、
**信頼できない判定器を評価経路から外せる。**

3 で分けるのは §11 の前例と同じである。§11 は「M_invariant の除外判定は max、
Arm C の色誤差は mean。混ぜてはいけない」と記している。
**座標誤差（0.044 units）と band confusion（11.29 units）は 2 桁違うため、
同じ土俵に乗せた瞬間にどちらの意味も壊れる。**

| 指標名 | 単位 | k=1 |
|---|---|---|
| 座標誤差 | px（3 軸合計、深度 8.60 換算） | 12.214 |
| **予約帯率** | ppm | **39.3** |
| **帯反転率** | ppm | **12.8** |

#### 1 回だけ行う測定

**帯反転 251 画素の空間分布（Target シルエットからの距離）。**

§11 は M_invariant から **Target シルエット ±2 px（AA フリンジ）を既に除外している。**
帯反転は背景と Target の境界で VAE がブレンドして起きるため、
2 px フリンジ内に収まっている可能性が高い。

| 結果 | 帰結 |
|---|---|
| 2 px 以内に収まる | **§11 が既に除外済み。追加対策なし** |
| 平坦な背景に散る | 別の問題。§29 の noise floor 側で扱う |

numpy のみで済む（`/workspace/w3b/vae_armb` の npy 4 本）。GPU 計算は不要。

予測（記録する）。**251 画素の 9 割以上が 2 px 以内に入る。**
予約帯 769 画素は境界に限らず散る（値域の端 = 床の Z 由来なので床全体に出る）。
**当たれば予約帯と帯反転は空間分布の違う別現象であり、分けてカウントする根拠が
強くなる。**
