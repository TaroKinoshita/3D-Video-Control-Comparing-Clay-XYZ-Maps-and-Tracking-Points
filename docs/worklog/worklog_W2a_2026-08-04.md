## 3. Renderer 軸の向きを決定

### 3.1 論点

学習に使う側（R0）を EEVEE と Cycles のどちらにするか。

| 論点 | EEVEE 有利 | Cycles 有利 |
|---|---|---|
| フリッカー | 決定的。ノイズゼロ | サンプル不足でフレーム間ノイズ。デノイザは時間的に不安定 |
| §12 State coherence の測定 | ターゲットが揺れないので生成側のフリッカーを純粋に測れる | **ターゲット自体が揺れると指標が意味を失う** |
| ベースモデルの分布への近さ | EEVEE Next は raytracing 入りでそこそこ寄る | GI・軟影があり実写寄り |

**1と2を優先した。** 3 は全 arm 共通で床が上がるだけで B vs C の比較には効かない。
§12 に「フリッカー」を State coherence の項目として置いている以上、
学習ターゲットが揺れているのは自己矛盾。

### 3.2 決定

```
R0 = EEVEE（学習に使う。Train / IID）
R1 = Cycles（汎化テスト用。生成のみ、評価は9月）
split は target video にのみ適用する
Control Video と幾何パスは全 split で同一（EEVEE 固定・bit 一致）
```

**Control 側に split を効かせない理由。** Arm A（クレイ＝レンダー）だけ Control に
domain shift が乗り、Arm B / C には乗らない。Renderer shift 評価が arm 間で
非対称になり、§2 の「異なるのは Control Video のみ」という前提が崩れる。

### 3.3 R1（Cycles）側の必須設定

| 設定 | 値 | 理由 |
|---|---|---|
| サンプル数 | 高め（暫定512） | 少ないとフレーム間ノイズ |
| デノイズ | 無効 | フレーム独立に効くので時間的な揺れを作る |
| Adaptive Sampling | 無効 | フレームごとにサンプル数が変わると揺れの量も変わる |
| Noise Seed | **固定** | 既定でフレームごとに変わる。固定するとノイズが静止する |

材質は Principled BSDF のみ。Color Management を両レンダラで統一。

### 3.4 撤回した発言

「Cycles で焼くコストを見積もったか」と問いかけたが、**これは過大に言った。**
データ量が小さい（Scene B/C + Calibration の数クリップ）ので、
832×480 × 49フレームを Cycles で焼いても現実的な時間で終わる。
コストは判断材料にならなかった。

## 4. W2a の設計 — なぜ極小シーンから始めたか

### 4.1 前提

エクスポータが吐くもののうち、**見て検証できるのは Arm A のクレイだけ。**

```
Arm A  クレイレンダー          → 見れば分かる
Arm B  World座標を色にしたもの  → 見ても分からない
Arm C  色付きの点               → 見ても分からない
GT     Depth / ObjID / Mask     → 見ても分からない
```

§17 の既知バグリストが全部「レンダーを見ても気づけない、数値を読んで初めて分かる」型。
本番シーンでは「その値が正しいか」を判定する基準が無い。

**正解が手計算できるシーンを作り、そこで配管を検証する。**
作法#9（正解が既知の合成データで検出器を先に検証する）の適用。
Depth 規約のときに順序を間違えた（実測の後に陽性対照をやった）ので、そのリベンジ。

### 4.2 潰す対象（4つの静かに壊れる経路）

| # | 経路 | 典型的な間違い |
|---|---|---|
| 1 | Position パス読み出し | World 座標のつもりが Object / Camera 座標 |
| 2 | Arm C の順投影 | **上下反転**（画像の行は上から、UVは下から） |
| 3 | Depth の読み出し | 読み出し先が正しいか |
| 4 | フレーム番号 | index 0始まり / Blender 1始まり の取り違え |

**2 が一番危ない。** 上下反転は「それっぽく見える」ので本番シーンでは絶対に気づけない。

### 4.3 シーンの設計要件

| 要件 | 理由 |
|---|---|
| 座標が手計算できる | 全 assert の基準 |
| **scale 1.0 / rotation 0** | 既知バグ#1 を構造的に排除。`matrix_world` が平行移動だけになる |
| 物体が動く | フレーム番号のズレを検出（静止してると気づけない） |
| 遮蔽が起きる | 遮蔽判定と「再出現時の同一点維持」を検証 |
| **左右・上下非対称** | **対称なシーンでは反転バグが検出できない** |
| 平らな壁がある | Position パスが広い面積で既知値を返す |

### 4.4 確定した構成

カメラを **+Y 方向**に向けることで `depth = world_Y + 10` になり計算が単純化される。

| オブジェクト | world 位置 | サイズ | 役割 |
|---|---|---|---|
| Wall | y = +2（深度12） | 12 × 12 | Position パスの既知値 |
| Target（立方体） | x = −1.8 → +1.8、y = 0 | 1 × 1 × 1 | 順投影・フレーム番号 |
| Occluder（板） | y = −3（深度7） | 0.7 × 3.0 | 遮蔽判定・再出現 |
| **Marker（立方体）** | (2.5, 1.9, 1.2) | 0.2 | **反転検出** |

カメラ `(0, −10, 0)` / `rotation (90°, 0, 0)` / 50mm / センサー36mm / HORIZONTAL

```
px_per_unit(d) = 1155.5556 / d
u = 416 + X × px_per_unit(depth)
v = 240 − Z × px_per_unit(depth)
depth = world_Y + 10
```

マーカーは u = 658.76 / v = 123.47（右上の象限）。左右反転すれば u = 173、
上下反転すれば v = 356 になるので、どちらの事故も一発で分かる。

Target の速度は 3.6 ユニット ÷ 48 = **8.667 px/frame**（設計上限12以内）。
遮蔽される区間は index 18-30。

## 5. W2a-0 — 極小シーン生成

**成果物** `build_min_scene.py` → `min_scene.blend` / `scene_spec.json`

### 5.1 実装方針

| 方針 | 理由 |
|---|---|
| scale 1.0 / rotation 0 に固定 | 既知バグ#1 を構造的に排除 |
| 平面は `from_pydata` で頂点直打ち | サイズ指定に scale を使わない。法線の向きも確定できる |
| 立方体は `primitive_cube_add` | **手で面を張ると内向きの面が混ざる**（§17 バグ5） |
| 補間は LINEAR | 既定の BEZIER は ease-in/out で等速にならない |
| 正解値を JSON に吐く | bpy を使わない素の式で計算。レンダリング経路と独立した照合基準 |

### 5.2 途中で潰した不具合

**立方体の面の巻き方向。** 頂点を手で並べて面を張ると法線が内向きの面が混ざる。
最初の下書きで実際にそうなっていた。`primitive_cube_add(size=...)` に任せると
Blender が正しい法線を作り、かつ object.scale は 1.0 のままになる。

**`Principled BSDF` をノード名で引いていた。** UI 言語によって名前が変わる可能性が
あるので `node.type == "BSDF_PRINCIPLED"` で探す形に変更。

### 5.3 実行時に発覚した Blender 5.2 の API 変更

```
AttributeError: 'Action' object has no attribute 'fcurves'
```

4.4 で導入された slotted actions により、F-Curve が
`action.layers[n].strips[m].channelbag(slot).fcurves` に移動していた。

対策を2段構えにした。

| 手段 | 内容 |
|---|---|
| 予防 | `preferences.edit.keyframe_new_interpolation_type = "LINEAR"` を先に設定 |
| 確認 | 新旧どちらの階層でも F-Curve を辿る `iter_fcurves()` で実際に LINEAR を強制 |

同時に self-check の穴も塞いだ。**補間が BEZIER でも index 24（区間の中点）は
対称なので一致してしまう。** 照合点を index 0 / 12 / 24 / 36 / 48 の5点に増やした。

### 5.4 訂正した記録

**キーフレーム終点の規則。** protocol.md rev.3 に「終点は Blender frame 50 に打つ」と
書いたが、**一方向運動では誤り。**

| 運動の型 | 終点 | 区間数 |
|---|---|---|
| **一方向（今回の Target）** | **frame 49** | **48** |
| ループ（W1 のラップアラウンド並進） | frame 50 | 49 |

frame 50 にすると 1フレームあたり 3.6/49 = 0.0735 になり、
最終フレームが X = 1.727（目標 1.8）で止まる。照合値 u = 624 が壊れる。

**EEVEE も平均化する。** rev.3 の §22.3 に「Cycles はサンプル平均するから幾何パスに
使わない」と書いたが、EEVEE も同じ問題を持つ。

```
scene.eevee.taa_render_samples  既定 64   ← 複数サンプルを平均
scene.render.filter_size        既定 1.5px ← ピクセル間でぼかす
```

§22.1 の Depth 規約検証は平らな板が相手だったので、平均しても値が変わらず気づけなかった。
**輪郭があるシーンでは効く。** 幾何パスは `taa_render_samples = 1` / `filter_size = 0.01` が必須。

### 5.5 結果

| 項目 | 実測 |

| Target velocity | 8.6667 px/frame（上限12） |

### 6.6 「許容超え 19 px」の追跡 — マスク定義の欠陥を発見

Depth 検査で 19 px が許容を超えた。EXR を直接読んで場所を特定した。

```
列 647 / 行 115-133（19行 × 1列）
world X = 2.3984（マーカーの −X 側面）
world Y = 1.9795
depth   = 11.9798  ← Y + 10 がぴったり成立
```

**Depth の問題ではなかった。** 壁マスクを `|Y − 2.0| < 0.05` で定義したため、
Y = 1.8〜2.0 のマーカー側面のうち Y ≥ 1.95 の帯が壁として拾われた。

**規定。マスクは `pass_index`（Object ID パス）で定義する。**
値の許容範囲では隣接する面が漏れる。§14 の assert に追加した。

### 7.4 検査C — 遮蔽判定の2方式（§18-17 の決着）

| 方式 | 幾何期待値との誤り（294判定中） |
|---|---|
| Depth パス比較 | **8** |
| **`ray_cast`** | **0** |

前面中心の隠れ区間は両方式とも [18, 30]（13フレーム）で事前計算どおり。

**Depth 方式が失敗した機序を特定した。** 食い違った8件は全部**側面中心**。

```
+X 側面は x = -1.3 の平面。y が -0.5→+0.5 で深度 9.5→10.5 に変化する。
ところが画面上の幅はたった 15.06 px。
深度の勾配 = 1.0 / 15.06 = 0.0664 / px
```

**1画素の中で深度が 0.066 も変わる。** 点は画素中心から 0.28 px ずれているので、

| 計算 | 値 |
|---|---|
| 点の深度 | 10.000 |
| 画素中心の深度 | 10 − 0.28 × 0.0664 = **9.981** |
| 実測 scene_depth | **9.982** |

index 3 でも検算が合う（面幅 12.46 px → 勾配 0.0803 → 9.978、実測 9.978）。

なぜ index 0, 3, 6, 9 だけか。

| 理由 | 説明 |
|---|---|
| 3フレーム周期 | 速度 8.667 px/frame × 3 = **26.0 px ちょうど**。サブ画素の位相が3フレームで一巡 |
| index 12 以降で止まる | u = 369.78 が**遮蔽板の u 範囲に入る**ので、両方式とも「遮蔽」で一致する |

**`EPS_DEPTH` を上げても解決しない。** このシーンでは 0.05 にすれば通るが
（実際の遮蔽は 2.5 units 離れている）、薄い物体や接触面があるシーンでは破綻する。
**閾値がシーン依存になる時点で使えない。**

### 7.5 決定

```
Arm C の遮蔽判定 = scene.ray_cast
  カメラ原点から点へレイを飛ばし、距離 (d - 1e-3) までにヒットがあれば遮蔽
  自己ヒット回避の 1e-3 以外にパラメータを持たない
```

protocol.md に残す理由の文言。

> Depth パス比較は、斜めに見える面で1画素内の深度勾配が許容値を上回るため
> 誤って遮蔽と判定する。必要な許容値はシーンの幾何に依存するので固定できない。

①を主にした理由は §0 の凍結思想と揃うから。**シーンファイルが「何を出力するか」を

`configure_passes()` を追加し、Position / Depth / Object Index を有効化、
**Mist を明示的に無効化**した。self-check にも同じ検査を入れて保存前に検出できるようにした。

### 9.6 通った項目で新たに確認できたこと

**S16（法線）が PASS。** 不安要素だったので潰せた。閉メッシュの符号付き体積が正
= `primitive_cube_add` の法線が外向き。壁と遮蔽板は開いたメッシュなので体積判定は
スキップされるが、`make_quad` で巻き方向を手計算し、self-check で
法線が −Y を向くことを検証済み。

**S18（速度）が 9.123 px/frame。** 追跡点の中心速度 8.667 より大きい。
bbox 8隅で測っているため。

| 測定対象 | 速度 |
|---|---|
| 立方体の中心（深度10） | 8.667 px/frame |
| **前面の隅（深度9.5）** | **9.123 px/frame** |

深度9.5 の px/unit = 121.638 × 0.075 = **9.123**。ぴったり合う。
**bbox 隅で測るのが正しい**（中心だけ測ると 5% 過小評価する）。

### 9.7 O08 の数字が W2a-3b と食い違う理由

```
contract_assert : 検査 354 成分 / 除外 190 成分
w2a3b           : 孤立点 484件
```

孤立の定義が違う。

| スクリプト | 孤立の定義 |
|---|---|
| W2a-3b | 他の**可視点の中心**が 2r+1 = 13px 以内に無い |
| contract_assert | 成分の bbox を r+1 = 7px 広げた領域に**他色の画素**が無い |

後者のほうが厳しい。基準が違っても結論（全部113）が同じなので問題ないが、
数字が食い違う理由は記録しておく。

### 9.8 O10 を WARN 固定にした理由

「同一色 == 同一点」は**出力画像だけでは原理的に検証できない。**
色が同じでも別の点かどうかは追跡情報が要る。O11 で割当ファイルとの突合はするが、
それは「割当が正しい」という前提に依存する。正直に WARN で残す。
