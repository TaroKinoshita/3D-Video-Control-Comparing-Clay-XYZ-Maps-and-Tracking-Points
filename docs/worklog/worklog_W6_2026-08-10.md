## 1. Scene C′（Arm C）の生成 — 完了

### 1.1 設計（確定）

Scene C′ = held-out 軌道変種。目的は §33.4(b) の「暗記経路と control 追従経路を区別して RQ1 に信号を残す」。

**軌道（raised-cosine 縦振り、前半に閉じ込め）:**

```
X(f) = -0.90 + 0.0375*f                    # Scene C Original 継承（触らない、u 不変）
Y(f) = Y0（一定）                           # depth 不変 → 面積不変（制約2 自動）
Z(f) = Z0 + A*(1 - cos(2*pi*f/35))/2   for f in [0,35]
     = Z0                              for f in [36,48]
A = 0.85,  Z0 = -0.80
```

`(1-cos)/2` を選んだ理由：f0 と f35 で値0かつ速度0（滑らかに始まり遮蔽窓入りで高さ復帰）、常に上方向のみ（床/Occluder下端はみ出しを構造的に回避）、山ピーク f17.5。

### 1.2 制約（4本）と充足

| # | 制約 | 値 | 充足 |
|---|---|---|---|
| 1 | 速度 | max\|screen_velocity\| ≤ 12 px/frame | ✅ 合成 max 11.40（設計）/ 描画後の縦移動 f17 で 122.7px |
| 2 | 面積 | Target 画面面積 ≥ Scene C | ✅ depth不変→占有率同一（円盤113px） |
| 3 | 始点 | frame0 の tv が Scene C と bit 一致 | ✅ **既存 armC_0000.png と画素完全一致（mkv経由でも）** |
| 4 | 遮蔽窓 | 36–40 で Target 完全遮蔽 | ✅ Target 可視0（Arm C は実際 35–41 が可視0＝7フレーム） |

**制約4は §33.4 の3制約には明示が無く、§12 の評価面「44フレーム(0–35/41–48)」から導出した隠れ制約。案 A（遮蔽窓を Scene C と同じ 36–40 に揃える）を採用。→ protocol rev.11 で明示。**

### 1.3 screen_velocity の定義（§26 実物）

**Target の bbox 最近隅（一番カメラに近い隅）の画面 px/frame。基準 depth = 8.60（pxu 134.3669）。** center（depth 9.00, pxu 128.3951）とは別。最近隅が最速なので速度上限判定として保守的。

### 1.4 Scene C の軌道リテラル（§26 で確定済みの再掲）

| 区間 | index | X | px/frame | Original / Edited |
|---|---|---|---|---|
| 通常 | 0→12 | −0.90→−0.45 | 5.0388 | 共通 |
| 停止 | 12→23 | −0.45 固定 | 0 | **Edited のみ** |
| catch-up | 23→36 | −0.45→+0.45 | 9.3023 | **Edited のみ** |
| 通常 | 36→48 | +0.45→+0.90 | 5.0388 | 共通 |

**Original は停止も catch-up も通らない。X を −0.90→+0.90 の等速直線（5.0388）。§10-519「Original は 6px/frame 以下」の設計通り、12 を余裕で満たす。**

### 1.5 Arm C 生成は Blender 不要だった（重要）

`score_armc.py` の `replay_frame` を読んで判明：**Arm C の control は Blender レンダではなく「240点を Python で円盤描画」**（disc radius 6px=113px、depth 遠い順に塗る）。点の u,v,depth,visible,rgb は `armc_points.json`（Scene C の bpy `select_arm_c.py` 出力、既存）にある。

C′ 化 = Target帯72点を **v シフト**するだけ：

```
u_new     = u_old                         （X不変→u不変）
depth_new = depth_old                     （Y不変）
v_new     = v_old − (1155.5556 / point_depth) × dZ(f)   ← 点ごとの depth で
visible   : f0-35 は Occluder矩形で再計算 / f36-48 は継承
```

**訂正（当初「一律 −134.36 で v シフト」と予測 → 外れ）**：Target はプリズムで点ごとに depth が違う（8.60–9.37）。正しくは点ごとの pxu。ピーク f17 の v シフトは 104.6–114.0px（一律ではない）。

**visible の再計算（当初「継承でOK」と予測 → 部分的に外れ）**：軌道が進むと Target 中心 u が 382→469 と Occluder u帯（401–567）に入る（f17–f35）。C′ は縦に上げるので、Scene C で Occluder に隠れてた点が上端(v233)を超えて見える。Occluder 矩形（u 401.56–567.67 / v 232.78–456.67 / depth 8.00）で再判定。Scene C で「frame 0–40 は矩形判定=レイキャスト完全一致、41–48 は7点ズレ（Occluder厚み0.05の縁）」を確認済みなので、**f0–35 は矩形再計算、f36–48 は継承**。結果、f8 以降で可視点が増える（f17: 44→60）。

### 1.6 Z0 = −0.80 確定（二重突合）

## 6. 偵察 run 判定 — 制御読めてる（暗記回避）★本セッション最大の結果

`gen_g1_armC.mkv` を `score_t_control.py` で判定：

| 指標 | 値 | 判定 |
|---|---|---|
| **T_control median** | **8.55 px** | ✅ PASS（≤47、floor 3.89 の約2倍） |
| T_control p95 | 42.00 px | ✅ <47 |

| tracker_fail | f34, f35 | 境界フレーム |

### 予測の答え合わせ（§33.7 / 本セッションの予測、すべて訂正）

| 予測 | 実際 | 判定 |
|---|---|---|
| §33.7「C′ 上で暗記に落ちる、Scene C 軌道が出る」 | control を読んで C′ 追従 | ❌ **外れ** |
| 「暗記なら T_control median が 47 超」 | 暗記でも median は両端0で薄まり 38（PASS しうる） | ❌ 外れ（陽性対照で判明、判定ロジックを Scene C 誤差比較に切替） |
| 「1本学習は暗記寄り」 | 制御獲得 | ❌ 外れ |

**結論：1本学習でも VACE control は強力で、暗記経路より control 追従が勝った。C′ center 誤差 8.55px（floor の約2倍）＝ほぼ完璧に control を追従。Scene C center とは 57px 離れており暗記していない。**

### 帰結（§33.7 段4）

- 暗記に落ちていない → **軌道変種の追加は不要 → 3 arm × S1 へ進める**
- **未決 #23（train 軌道本数 N）は「増やさない（N=1）」に傾く**（偵察 run 1本の結果に基づく暫定判断）
- Claim Gate が意味を持つ：暗記でないなら arm A/B/C で control 追従性能に差が出るはず。その差 vs Pipeline floor で主張可否
