### W7-02 「W2 が本体、W4 は残骸」→ **外れ（ただし結論は W2 が本体で正しい）**

`build_scene_c.py` が W2 と W4 の 2 箇所にあり、W4 の方が新しかった（08/11 20:30 vs 08/04 14:42）ため「W4 が最新版」という報告を受けて一度は「古いファイルを改修してしまった」と判断した。

派生した教訓：差分の中身を見る前にタイムスタンプで判断するとこうなる。`Compare-Object` を先に打つべきだった。

## 3. 本セッション最大の発見：`location.z = Z0 + dZ` は誤り

`scene_c_prime_traj.json` の meta にこう書かれていた。

```
"Z0_note": "location_z = Z0 + dZ ; Z0 MUST be read from Scene C Target in Blender"
"Z0_placeholder": -0.770651
```

**これに従うと壊れる。**

`build_scene_c.py` の `animate_target` は `obj.location = (x, 0.0, 0.0)` として **`index=0`（X）だけ**キーフレームを打っている。つまり **Scene C において `obj.location.z` は 0.0**。Target 幾何中心の Z（−0.80）は `TARGET_Z = (-1.50, -0.10)` として**メッシュ頂点に焼かれている**（作法#14：サイズは scale ではなくメッシュ頂点に焼く）。

したがって正しいのは **`location.z = dZ`**。`Z0 + dZ` にすると −0.80 を二重に足して中心が −1.60 に沈み、床（top Z = −1.50）を貫通する。

さらに `Z0_placeholder = -0.770651` は幾何中心 −0.80 とも一致しない。`gen_scene_c_prime.py` を読むと出所が判明した：

```
Z0_PLACEHOLDER = (240.0 - (252.3+434.8)/2.0) / (1155.5556/8.60) = -0.770651
```

点群重心の v 範囲 [252.3, 434.8] から depth 8.60 で逆算した推定値。幾何中心（depth 9.00）とは別物。同様に meta の `depth: 8.60` は bbox 最近隅であり、中心 depth 9.00 とは異なる。

**結論：meta は使わず `keyframes[].dZ` のみ使う。** rev.12 変更1 に明記した。

### 4.4 `render_target_video.py`（5 箇所、案1 採用）

このスクリプトは `open_mainfile` で `.blend` を読んだ**直後に `animation_data_clear()` でキーフレームを捨て**、`target_x()` で X を再計算して `location` に直接代入する設計（fcurve を信用しない作法）。**そのため `.blend` の Z キーフレームは伝わらない。**

- 案1（`animation_data_clear()` を維持し `target_z()` を足す）を採用
- 案2（`animation_data_clear()` を削除して `.blend` のキーフレームを使う）は不採用。`target_x()` は float64 で補間してから float32 に代入、fcurve は float32 で評価するので 1 ULP ずれる可能性があり、**既存 tv の frozen content sha を壊すリスク**を取る理由がない

改修：`scene_c_expect` の import / `target_z()` / `project_centre()` / `check_position()` / location 代入 3 箇所に Z 追加 + `check_position()` 挿入。

回帰確認：`original` の再レンダが既存 `RENDER\tv\R0S0\original` と **5/5 bit 一致**。案1 の前提が成立。

### 4.5 `export_geometry.py`（案1 + v_top 検査）

`animation_data_clear()` を呼んでいないため **Z は自動で反映される。`target_z` の追加は不要。**

一方で `visible_u()` の 1 次元遮蔽判定が C′ で 24 フレーム（index 6–29）誤判定する。詳細は rev.12 変更6。

改修：`prime_band_px()` / `visible_u()` の 2D 化 / `visible_u_1d()`（境界フレームの代替解）/ 境界フレームの両解許容 / **`target_v_top` 検査**（ID マスクの最上行 → v）。

`geo_expect.py` に `PRIME_TARGET_V_TOP` 49 行 + `PRIME_OCCLUDER_TOP_V` + `PRIME_BAND_SUBPIXEL_PX` を追記。

### 4.6 `render_arm_a.py`（tv と同一方式）

`target_z()` / `project_centre()` / `check_position()` + location 代入 3 箇所。ロジックは tv で SELFTEST 済み。

### 4.7 `encode_arm_b.py`（B 最大値検査）

**コード本体は無改修で prime に対応していた**（`--variant` を受け取り、`NORM_BOX` は spec 参照、`target_f1` は index 0 限定なので dZ=0 で通る）。

追加したのは検査のみ：`target_b_max` / `target_b_min` / Target 帯の内包確認。`armb_expect.py` に `PRIME_TARGET_B_MAX` 49 行 + `PRIME_TOL_ZLEVEL = 2` + `PRIME_B_SCALARS` を追記。

S/N：検出すべき信号は 20 段階（177–197）、誤差要因は合計 0.25 段階（1px の Z 誤差 0.181 段階 + Position パス誤差 0.061 段階）。

### 4.8 `png_to_ffv1.py`（sha 方式B の併記）

`content_sha256_b()` を追加、`encode` / `verify` の出力に方式 A / B を併記。既存の方式A は残す（既存 JSON 記録との整合）。

### 4.9 新規：`sha_probe.py`

mkv の content sha を 6 方式（A shape+tobytes / B tobytes / C per-frame / D BGR / E CHW / F file）で計算し、記録値と自動照合する診断ツール。合成データで A〜E が実際に別の値を出すこと（B と C は同一バイト列なので一致するのが正しい）を事前確認済み。

## 8. 会話の進め方（W7 で有効だったこと）

- **予測を先に置いて外れたら訂正明示**：W7 で 6 件の訂正が出た。特に W7-05（`frac_0` のピークが dZ のピークとずれる）は予測していなければ気づかないまま通過していた
- **assert は壊したデータで発火確認**：4 種の壊し方（Z 未反映 / Z0 を足す / dZ 半分 / clamp 除去）で全ての検査が発火することを確認してから実機に回した。特に「Z 未反映」は改修前のコードで **c1/c3/c4/NORM_BOX の全てを素通り**し、追加した v 判定だけが捕まえた
- **API・記録値を推測しない**：sha の不一致は「方式の違いだろう」で済ませず、記録値が既知の 3 本で 6 方式を総当たりして確定させた
- **一度に一つ決める**：案1/案2 の選択を都度確定してから実装した。特に `render_target_video.py` の案1（frozen sha を守る）は後の 5/5 bit 一致で正しさが裏付けられた
- **回帰を先に取る**：prime を焼く前に必ず original で回して既存成果物と bit 比較した。これで「改修が既存を壊していない」を毎回確認できた
