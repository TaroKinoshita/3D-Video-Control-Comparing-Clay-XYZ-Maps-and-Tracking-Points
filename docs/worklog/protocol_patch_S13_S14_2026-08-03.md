## §13.x Arm C（Object-Aware 3D Tracking）の点仕様

### 確定値

| 項目 | 旧（ラウンド1-2） | **新（ラウンド4）** | 変更理由 |
|---|---|---|---|
| 点の半径 | 3 px | **6 px** | 3pxは静止画でも色誤差14で余裕が無く、動くと崩壊する |
| 色の付け方 | 局所最大分離パレット12色 | 変更なし | — |
| 分離割当半径 | 24 px | 変更なし | — |
| 密度 | 0.3 点 / 空間潜在セル | **未確定**（測定時は全画面480点） | 対象物体上の必要点数が未定のため保留 |
| **V_max** | 未測定 | **≥ 17 px/frame** | 17まで検証済み。上限は未測定 |

### V_max の定義と条件

```
V_max = VAE往復後も点の色が識別可能な、スクリーン空間での最大速度
測定条件: 一様並進 / 視差なし / ラップアラウンド / 832×480 / 49フレーム / bf16
判定基準: 色誤差 ≤ 24（= 局所最小色間距離 48.1 の半分）
```

**「≥ 17」は下限。** 17より速い条件は測っていない。半径6の色誤差は
V=17で11.3と上限24の半分以下なので、さらに余裕がある可能性は高い。

### Blender アニメーション設計への制約

| 半径 | V_max | 49フレームで動ける距離 | 画面幅832pxに対して |
|---|---|---|---|
| 3 px | 3 px/frame | 144 px | 17% |
| **6 px** | **≥ 17 px/frame** | **≥ 816 px** | **ほぼ横断可** |

半径6を採用することで、当初想定していた「16fpsで3秒＝画面横断」の
物体運動が設計可能になった。§10 の編集区間（frame 12-23 で停止/減速）とも矛盾しない。

**ただし条件付き。** 測定は一様並進（画面全体が同じ方向に同じ速さでスライド）
で行った。実シーンではカメラ運動により視差が生じ、手前と奥で速度が異なる。
この条件は未検証なので、シーン設計時は V_max に安全率をかける
（例: 0.7倍 → 12 px/frame）ことを推奨する。

### 未確定として残す項目

1. **半径6での点数上限。** 480点（占有12.8%）でしか測っていない。
   点を増やすと Arm C の空間解像度は上がるが、重なりが増え、
   Arm B（密なWorld-XYZ場）との差が曖昧になる。
   → Blender のシーンを作り、対象物体に何点乗るかを見てから決める。
2. **V_max の真の上限。** 17より上は未測定。
3. **視差ありの条件。** 一様並進より厳しくなる可能性がある。

## §13.y 評価指標の変更 — identity から色誤差へ

### 変更内容

```
旧: identity復元率（近傍照合）を主指標とする
新: 色誤差（正解位置における8bit平均絶対誤差）を主指標とする
    identity復元率は補助指標として併記する
```

### 変更理由

identity復元率は**点の密度に強く依存する**ことが実測で判明した。

| 条件 | 半径 | 点数 | 平均近傍数 | identity(V=17) | 色誤差(V=17) |
|---|---|---|---|---|---|
| A | 3 px | 1872 | 6.8 | 49.3% | 29.77 |
| B | 3 px | 480 | 2.4 | **85.7%** | 23.73 |
| C | 6 px | 480 | 2.4 | 93.8% | **11.30** |

A と B は**半径も速度も同一で、点数だけが違う。** それだけで identity が
36ポイント動く。紛らわしい相手が減っただけで、点の品質は変わっていない。

```
identity = 点の品質 × 近傍の紛らわしさ  ← 混合物
色誤差   = 点の品質そのもの              ← 分離済み
```

Arm A / B / C は表現の密度が本質的に異なるため、identity で横比較すると
「点が疎な表現ほど高スコア」というバイアスが入る。RQ1（適応コスト）の
評価でこれを使うと結論が歪む。

### 併記のルール

identity を報告する場合は、必ず次を添える。

- 点数と平均近傍数
- 同一条件の V=0 ベースライン（絶対値ではなく落差で読む）

| 項目 | 値 | 備考 |
|---|---|---|
| 潜在形状（通常） | `[1, 16, 13, 60, 104]` | 49フレーム → 13潜在 |

**Phase 0.0 の VAE 作業に大容量GPUは不要。** LoRA学習の29.4GBとは別物で、
VAE往復は4.5GBで足りる。RTX 3090クラスで完結する。
大容量GPU（PRO 6000）が必要になるのは Main Training 以降。

### DiffSynth 2.0.18 の API 注意点


## §14.a Depth 規約の確定

### 確定値

| 項目 | 値 |
|---|---|
| **Blender Depth パスの規約** | **A（Z-depth：カメラ平面からの垂直距離）** |
| 検証バージョン | Blender **5.2.0** / EEVEE（`BLENDER_EEVEE`） |
| 解像度 | 832 × 480 |
| Mist パス | **GT 用途では使用不可** |

### 2つの規約の定義

```
A) Z-depth       カメラ平面からの垂直距離。光軸方向の成分のみ
B) Ray distance  カメラ原点から点までレイに沿った実距離（斜辺）

関係式  B = A / cos(θ)     θ = 光軸からの角度
画面中心（θ=0）では A = B。端に行くほど乖離する
```

### 検証方法

カメラに完全正対した平面を置き、Depth パスが全域で一定値を返すかを見る。

| 設定 | 値 |
|---|---|
| 平面 | size 20、原点 (0,0,0) |
| カメラ | (0,0,5)、rotation (0,0,0)（真下向き） |
| 焦点距離 / センサー | 18 mm / 36 mm |
| 水平半画角 | 45.0° |
| サンプル位置 | 画面中央行の center / left(x=4) / right(x=W-5) |

### 実測結果

| 位置 | 実測 | 規約A の予想 | 規約B の予想 |
|---|---:|---:|---:|
| center | 5.0 | 5.0 | 5.0 |
| left | **5.0** | 5.0 | 7.071 |
| right | **5.0** | 5.0 | 7.071 |

**陽性対照。** 端の角度が 45.0° あるため、規約B なら 7.071（差 41%）が
出るはずだった。それが出ていないので「感度不足で見分けられなかった」
可能性は排除される。

### Mist パスを除外する理由

Mist は 0〜1 に正規化された霧の濃さで、Start / Depth 設定に依存する相対値。
絶対距離ではないため GT には使えない。

## §14.b 各 Arm と Depth の関係

### 確定した役割分担

| 対象 | Depth を使うか | 作り方 | 規約の影響 |
|---|---|---|---|
| Arm A（Clay Previs） | **使わない** | クレイレンダーのみ | なし |
| Arm B（Dense World-XYZ） | **使わない** | **Position パス直接** | なし |
| Arm C（3D Tracking） | **使わない** | **`bpy` で頂点座標直接** | なし |
| VGGT 評価の GT | **使う** | Depth パス | **ここだけ効く** |

### Arm A に Depth を入れない理由

Arm A の役割は「外観ベースの素朴な統制条件」。Depth を足すと
「外観 + 幾何」のハイブリッドになり、Arm B との差が説明できなくなる。
RQ1（適応コスト）で差が出ても、外観由来か幾何由来か切り分け不能になる。

なお、クレイレンダーの陰影自体が法線由来の暗黙的な幾何情報を含んでいる。
明示的な Depth を足すのは二重取りにあたる。

### Arm B / C が逆投影を通らない理由

どちらも Blender シーン内に正解の 3D 座標が既に存在するため、
Depth からの逆投影が不要。EEVEE の Position パス（View Layer Properties →
Passes → Data → Position）で World 座標を直接出力できることを確認済み。

**副次的な利点。** 逆投影を通さないことで、`fov` 由来のバグが
Arm B / C に混入する経路が消える。fov 誤りと規約誤りは
「画面端ほど座標がズレる」という同一の症状を示すため、
両方が同時に効きうる経路は減らすほど良い。

## §14.c レンダラの選定

| 用途 | レンダラ | 理由 |
|---|---|---|
| Arm A（クレイ） | **EEVEE** | 高速・ノイズなし・GI 不要 |
| Position / Depth パス | **EEVEE** | Position パスの存在を確認済み |

**Cycles を使わない理由。** Cycles は 1 ピクセル内の複数サンプルを平均する。
色ならアンチエイリアスになるが、Depth や Position を平均すると
物体の輪郭に「手前と奥の中間値」＝実在しない座標が生成される。
輪郭は本研究で最も重要な領域であるため、これは許容できない。

やむを得ず Cycles を使う場合はサンプル数を 1 にする。

**全レンダラ共通で必ず無効化するもの**

- モーションブラー
- 被写界深度（DoF）
- デノイズ

いずれも深度・座標を空間的に混合するため。

## §14.d VGGT 側の規約（暫定）

| 項目 | 状態 |
|---|---|
| 推定される規約 | **A（Z-depth）** |
| 確度 | **強いが間接。コード未確認** |
| 実地検証 | **Day 25-31（VGGT 初回起動時）** |

### 根拠

VGGT の README では、カメラヘッドの出力を OpenCV 規約の
extrinsic / intrinsic に変換し、`unproject_depth_map_to_point_map(
depth_map, extrinsic, intrinsic)` で 3D 点群を構成している。

intrinsic 行列 K を用いた逆投影の標準形は次の通り。

```
3D点 = z × K⁻¹ × (u, v, 1)
```

この `z` は光軸方向の成分であり、レイ距離を代入すると画面端で座標が
破綻する。**K を用いる実装は必然的に規約 A。**

同系統の point-map 表現を用いる研究でも、深度はカメラローカル座標系の
光軸 z 方向として定義されるのが通例。

### 検証を Day 25-31 まで遅らせる判断

これは「予測を信じる」のではなく「検証がタダになる時点まで遅らせる」判断。

1. **賭け金が小さい。** Arm B / C は規約を通らないため、誤りの影響範囲は
   評価パイプライン 1 本に限定される。
2. **専用実験が不要。** VGGT の初回起動時に §14.a の平面シーンを
   そのまま入力すれば済む。5.0 を返せば A、7.071 を返せば B。
3. **今やると GPU 起動が必要。** 平面 1 枚のために Pod を立てるのは
   順序が悪い。

## §14.e Blender 5.2 の API 変更（実装上の注意）

**Blender 4.x 時代のサンプルコードはほぼ動作しない。** Day 11-17 の
エクスポータは 5.2 前提で書く。

| 旧 API | 新 API |
|---|---|
| `scene.node_tree` | **`scene.compositing_node_group`**（5.0 で削除） |
| `scene.use_nodes = True` | **非推奨**。常に True を返し、設定は無効 |
| Composite ノード | **削除**。Group Output ノードを使う |

コンポジタのノードツリーはシーンの一部ではなく独立したデータブロックに
なった。生成手順は次の通り。

```python
tree = bpy.data.node_groups.new("名前", "CompositorNodeTree")
scene.compositing_node_group = tree
rl = tree.nodes.new("CompositorNodeRLayers")
```

Viewer ノード（`CompositorNodeViewer`）は 5.2 でも動作する。
出力は `bpy.data.images["Viewer Node"].pixels` から RGBA 4ch で読める
（Depth は R チャンネル）。

なお `print()` の出力は Info エディタではなくシステムコンソールに出る
（Windows: Window → Toggle System Console）。
